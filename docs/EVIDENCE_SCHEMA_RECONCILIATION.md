## 1. 충돌의 정확한 범위

```
$ comm -12 <v11 표 19개 정렬> <내 표 15개 정렬>
earthus_evidence_edge
earthus_evidence_node
```

**이름이 겹치는 것은 정확히 2개다.** 그 밖에:

| 개념 | v11 초안 | 내 파일 | 관계 |
|---|---|---|---|
| 증거 노드 | `earthus_evidence_node` | `earthus_evidence_node` | **이름 충돌** |
| 증거 관계 | `earthus_evidence_edge` | `earthus_evidence_edge` | **이름 충돌** |
| 사건 | `earthus_event_cluster` + `earthus_event_cluster_member` | `earthus_earth_event` (+ `earthus_event_evidence` · `earthus_news_article.event_id`) | **이름은 다르지만 의미가 중복** |
| 특성값·여행·오염·기억·모델·보정·릴리스·개인문맥·파일럿·릴리스감사 | 15개 표 | 없음 | 중복 아님 |

⚠️ 의미 중복이 이름 충돌보다 위험하다. 이름이 다르면 둘 다 만들어지고,
**사건의 정본이 둘이 된다** — 어느 표가 진실인지 코드가 판단할 수 없다.

## 2. `earthus_evidence_node` 전문 비교

```sql
-- v11 초안
create table if not exists public.earthus_evidence_node (
  evidence_id text primary key, evidence_kind text not null, source_id text not null,
  external_id text, title text, observed_at timestamptz, source_url text,
  payload jsonb not null default '{}'::jsonb, created_at timestamptz not null default now()
);
```

```sql
-- 내 파일 (차이만 표시)
  evidence_kind  text not null check (evidence_kind in (…8종…))     ← CHECK 추가
  source_id      text not null references public.earthus_source(source_id) on delete restrict
                                                                      ← 외래키 추가
  source_kind    earthus_source_kind not null                        ← 신규 칸
  truth_status   earthus_truth_status not null default 'UNKNOWN'     ← 신규 칸
  + index (source_id)
  + index (evidence_kind, observed_at desc)
```

| 항목 | v11 | 내 파일 | 차이의 의미 |
|---|---|---|---|
| PK | `evidence_id` | 같음 | — |
| `evidence_kind` 제약 | **없음** (자유 text) | CHECK 8종 (v11 `contracts.js EVIDENCE_KINDS` 와 동일) | v11 스키마는 어휘 밖 값을 받는다. 코드(`requireEvidenceKind`)가 막지만 DB 는 안 막는다 |
| `source_id` FK | **없음** | `earthus_source` 참조 · `on delete restrict` | v11 스키마에서는 출처가 사라져도 증거가 남는다 → **근거 사슬이 DB 수준에서 끊긴다** |
| 3축 파생값 | 없음 | `source_kind` · `truth_status` | `TRUTH_VOCABULARY_CANONICAL.md` 의 3축을 담을 자리 |

## 3. `earthus_evidence_edge` 전문 비교

```sql
-- v11 초안

  from_evidence_id text not null references …(evidence_id) on delete cascade,
  to_evidence_id   text not null references …(evidence_id) on delete cascade,
  relation text not null,                          ← CHECK 없음
  metadata jsonb not null default '{}'::jsonb,
  unique(from_evidence_id, to_evidence_id, relation)
```

```sql
-- 내 파일
  relation text not null check (relation in (…9종…)),          ← CHECK 추가
  created_at timestamptz not null default now(),               ← 추가
  primary key (from_evidence_id, to_evidence_id, relation),    ← 대리키 대신 자연 복합키
  constraint … check (from_evidence_id <> to_evidence_id),     ← 자기참조 금지
  + index (to_evidence_id)
```

| 항목 | v11 | 내 파일 | 판단 |
|---|---|---|---|
| PK | 대리키 `id bigint identity` + unique 제약 | 자연 복합키 | **기능 동일.** 대리키는 불필요한 열이다. 다만 v11 쪽이 나쁜 설계는 아니다 |

| 자기참조 | 허용됨 | 금지 | `trace()` BFS 가 자기 자신으로 도는 것을 막는다 |
| 역방향 인덱스 | 없음 | `(to_evidence_id)` | `trace()` 는 양방향으로 훑는다 — 없으면 전수 스캔 |

```sql
-- v11 초안

  latitude, longitude, status default 'UNKNOWN', official_safety, confidence double precision
```

| 항목 | v11 `earthus_event_cluster` | 내 `earthus_earth_event` | 판단 |
|---|---|---|---|
| S3 정본 포인터 | **없음** | `canonical_s3_key` · `canonical_sha256` · `canonical_schema` · `canonical_written_at` + 유일 인덱스 | **결정적 차이.** v11 설계는 Postgres 를 정본으로 본다. 사용자가 확정한 "EarthEvent canonical source = S3, Postgres = index/trace" 와 어긋난다 |
| 시각 | `started_at` · `updated_at` (2칸) | `occurred_at` · `issued_at` · `updated_at` · `retrieved_at` (4칸, `retrieved_at` 만 NOT NULL) | 시각 4분법(`intel-feed.js` F01 기록). v11 은 "일어난 때"와 "발표된 때"를 구별하지 못한다 |

| 신뢰도 | **`confidence double precision`(0~1)** | 없음 | ⚠️ **숫자 신뢰도 칸이 지시서와 충돌한다.** "임의 confidence percentage 를 생성하지 않는다" 가 PHASE 5 요구다. 칸이 있으면 채우고 싶어진다. 정본 어휘는 `CONFIDENCE` 4단계다 |
| 위치 의심 | 없음 | `location_doubt` + 확정 승격 금지 CHECK | gdelt `placeDoubt` 계보 |
| 구성원 모델 | 일반 `member_kind` 한 표 | 타입별 분리 — `news_article.event_id` · `event_evidence` · `event_timeline` | 일반 표는 무엇이든 담을 수 있어 제약을 걸 수 없다 |
| 좌표 완결성 | 없음 | `(latitude is null) = (longitude is null)` CHECK | 한쪽만 있는 좌표가 0도로 찍히는 것을 막는다 |
| 원본 사건 중복 | 없음 | `unique(source_system, source_event_id)` | 같은 USGS 사건이 두 번 색인되는 것을 막는다 |

### 5.1 v11 초안을 어떻게 다루나

**파일을 수정하지 않는다.** 두 사본이 추적돼 있고 v11 작업의 산물이며, 나머지 15개 표는 유효하다.
대신 이 문서가 **대체 관계를 기록**하고, 내 SQL 이 **적용 시점에 충돌을 잡는다**(§6).

```
v11 초안에서 대체된 것 (적용하지 않는다)
  earthus_evidence_node          → aws/_shared/sql/20260913… 의 같은 이름 표
  earthus_evidence_edge          → 같음
  earthus_event_cluster          → earthus_earth_event
  earthus_event_cluster_member   → earthus_news_article.event_id · earthus_event_evidence · earthus_event_timeline

v11 초안에서 유효한 것 (이번 범위 밖, 그 기능을 배선할 때 떼어 온다)
  earthus_intelligence_feature_value · earthus_travel_discovery_result · earthus_travel_best_window
  earthus_pollution_event · earthus_pollution_transport_run · earthus_public_action_event
  earthus_memory_signature · earthus_memory_match · earthus_intelligence_model
  earthus_forecast_ground_truth · earthus_calibration_metric · earthus_intelligence_release
  earthus_user_context_v2 · earthus_intelligence_pilot_measurement · earthus_intelligence_release_audit
```

⚠️ v11 초안을 **부분 적용**하려면(15개만) 그 파일을 그대로 붙여 실행할 수 없다 —
겹치는 4개까지 함께 만들어진다. 그때는 15개만 뽑은 새 파일을 만든다. 이번 범위가 아니다.

## 6. 조용히 망가지는 경로를 막았다

이 조사에서 찾은 실제 위험:

> **양쪽 다 `create table if not exists` 다.**
> v11 초안을 먼저 적용한 DB 에 내 파일을 돌리면 `create table` 이 **no-op 으로 지나가고
> 아무 오류도 나지 않는다.** 결과: `source_kind`·`truth_status` 칸 없음, `source_id` FK 없음,
> `evidence_kind` CHECK 없음 — 그런데 "적용 성공"으로 보인다.
> 조립기는 그것을 모르고 쓰다가 런타임에 다른 곳에서 터진다.

그래서 내 SQL 맨 앞(`begin;` 직후, 어떤 표보다 먼저)에 가드를 넣었다:

```sql
do $$ begin
  -- ① v11 모양의 evidence 표가 이미 있다 (source_kind 칸이 없다)
  if exists (…earthus_evidence_node…) and not exists (…column_name = 'source_kind'…) then
    raise exception … 'SCHEMA_CONFLICT: earthus_evidence_node 가 이미 있으나 source_kind 칸이 없다'
      hint = 'docs/EVIDENCE_SCHEMA_RECONCILIATION.md §5 의 이행 절차를 먼저 수행하라.';
  end if;
  -- ② v11 쪽 사건 표가 이미 있다 — 사건 정본이 둘이 된다
  if exists (…earthus_event_cluster…) then raise exception 'SCHEMA_CONFLICT: …'; end if;
  -- ③ 내 사건 표가 다른 모양으로 이미 있다 (canonical_s3_key 칸이 없다)
  … raise exception …
end $$;
```

**가드는 고치지 않는다 — 멈춘다.** `alter`·`drop` 을 실행하지 않는다.
전체가 `begin; … commit;` 안이라 예외가 나면 아무것도 만들어지지 않는다.

시험 6개가 이를 검사한다(`test_migration_sql.py::ConflictGuardTests`):
가드가 표 생성보다 먼저 오는가 · 세 조건을 각각 검사하는가 · 이 문서를 가리키는가 ·
실행 구간에 `alter`·`drop` 이 없는가.

### 9.1 남은 이름 모호성 1건 — 기록

`aws/report-engine/generator.py`(추적) 와 `aws/distribution/generator.py`(미추적)가
**같은 모듈명**이다. 각자 자기 디렉터리를 `sys.path` 앞에 넣어 지금은 올바르게 해석되지만,
한 프로세스에서 둘을 다 import 하면 먼저 들어온 쪽이 이긴다.
같은 문제가 `validation.py`·`cli.py`·`handler.py` 에도 있다.

이것은 **DB 스키마가 아니라 Python 모듈 이름의 모호성**이다. 이번 마이그레이션과 무관하지만
`UNTRACKED_BASELINE_AUDIT.md` §5 의 오탐 원인이었으므로 여기 적어 둔다.
DB 표 이름에는 모호성이 없다 — 전부 `earthus_` 접두사이고 시험이 중복을 검사한다.

## 11. 남은 것

1. 사용자가 v11 대체 결정을 승인한다 (이 문서 §5)
2. Supabase SQL Editor 에 내 파일을 적용한다 — 가드가 먼저 돌아 충돌을 잡는다
3. 적용 후 표 15개·도메인 4개 존재를 확인한다
4. v11 초안의 남은 15개 표가 필요해지면 그것만 뽑은 새 파일을 만든다
5. `aws/distribution/generator.py` 등 모듈명 모호성은 별건으로 다룬다(§9.1)
