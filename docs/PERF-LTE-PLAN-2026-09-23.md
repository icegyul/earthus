# 폰 LTE 첫 화면 속도 — 원인과 고칠 순서 (2026-09-23)

> PD 말씀(2026-09-23): "v1 접속하면 256개 로딩 뜨면서 기다리는데 … 가장 최적화 방법 찾아 모바일에서 특히 lte 모드에서 볼때 굉장히 오래걸려"

> 이 문서는 **계획**이다. 저장소 코드·캐시·배포는 아무것도 바꾸지 않았다. 조사 보고서 4건(v1 첫 화면 경로 · v2 바이트 · 캐시·전달 · LTE 기준선)을 서로 대조해 합쳤다.
> 표기: **실측** = 재서 나온 값 · **추정** = 계산값(식을 같이 적음) · **LH** = Lighthouse 모의값.
> 측정 자료 폴더: `build/perf-investigation/` (git 제외). 기준선 결과: `build/perf-investigation/baseline-20260923-204802.json`.

## 1. 한 줄 결론 + 지금 수치

**"256개 로딩"은 v1 이 아니라 v2(`/v2/`) 화면이다. 그 256은 지형 타일 256장(18.5 MB)이고, 이것이 폰 LTE 첫 방문을 21.5초, 나쁜 LTE에서 108초로 만든다. 가장 먼저 고칠 것은 이 지형 타일이다. v1 은 첫 방문 3.3초·재방문 0.85초로 v2 보다 훨씬 가볍다. 다만 나쁜 LTE에서는 로딩 화면이 걷힌 뒤에도 지구가 약 9.5초 검게 남는다.**

- 근거: `256` 은 v1 `prototype/index.html`·`prototype/js/main.js` 에 **0번** 나온다(grep).
- "N/256" 을 찍는 곳은 v2 한 곳뿐이다: `prototype/v2-three/js/main.js:2306-2308` `` `${i18n.t('loadTerrain')} ${done}/${tot}` ``. 표시 문구는 `v2-three/js/i18n.js:77` "지형 데이터 로딩" 이다.
- 타일 수는 `main.js:138` `TERRARIUM_ZOOM = 4` 에서 16×16 = 256장으로 정해진다.
- ⚠️ **PD 확인 요청**: 느렸던 주소가 `earthus.net/` 인지 `earthus.net/v2/` 인지 알려주세요. 이 문서는 "v2 였다"로 보고 순서를 정했다. v1 개선안도 아래에 같이 있다.

¹ **v2 LTE 첫 방문**
- 표의 중앙값은 29.1 s 이지만 다른 세션과 CPU 가 겹친 두 회차가 끌어올린 값이다.
  - 오염된 회차: 긴 작업 6.2 s·7.7 s, PC CPU 58 %·82 %.
  - 깨끗한 회차 r3: 21.5 s. 따로 돌린 두 번도 21.47 s·21.93 s 였다.
  - 그래서 기준값은 21.5 s 로 둔다.
- 받는 양만으로 정해지는 최소치는 20.96 MB ÷ 1.125 MB/s ≈ 18.6 s 다(계산).
- globe 33.4 s 는 오염 회차가 섞인 중앙값이다. 깨끗한 회차의 globe 값은 보고되지 않았다.

**단위 주의.** 기준선 표의 "MB" 는 **MiB**(÷1,048,576)다 — `lte-baseline.mjs:374, :447` 확인. 회선 속도는 십진 B/s 다(LTE 9 Mbps = 1,125,000 B/s · RTT 70 ms · CPU×2, 나쁜 LTE 1.6 Mbps = 200,000 B/s · RTT 150 ms · CPU×4, `lte-baseline.mjs:17-18`).
- 그래서 19.99 MiB = 20.96 MB, 지형 17.69 MiB ≈ 18.55 MB 로 LH 의 18.54 MB 와 같다.
- 캐시 보고서가 global.png 를 "5.26 MB" 라고 적은 것도 같은 단위 차이다(5,381,747 B ÷ 1024 ÷ 1000 ≈ 5.26). 실제 크기는 S3 head-object 의 **5,381,747 B** 다.

**Lighthouse 수치는 목표로 쓰지 않는다.**
- v1 LCP 48.9 s 는 모의값이다.
  - 실측 LCP 2,137 ms 전에 끝난 요청 9.56 MB 를 느린 4G(1.47 Mbps)로 다시 계산한 것이다. 9.56 × 8 ÷ 1.47 ≈ 52 s.
  - 출처: lighthouse-v1.json `metrics.observedLargestContentfulPaint`.
- v2 LCP 6.3 s 는 지구가 아니라 로딩 화면 로고다.
  - 요소는 `div#loading > img.lockup` 이다(`lcp-discovery-insight`).
  - 기준선의 v2 LCP 요소도 `img.lockup` 이다.
- 체감 속도는 위 표의 **loader·globe** 로 본다.

**과제 전제 두 가지를 정정한다.**
1. "v1 모듈 전부 no-cache" 는 헤더상 사실이 아니다.
   - 실측은 108개 중 `no-cache` 36개, `max-age=60` 72개다(`build/perf-investigation/v1-modules-cc.tsv`).
   - 다만 서비스워커가 스크립트·스타일을 모두 `cache:'no-cache'` 로 다시 확인한다(`prototype/sw.js:104-105, :120`). 그래서 재방문에서는 **실효상 전부 no-cache** 다.
2. 오늘 먼저 알려진 v1 수치(첫 방문 2.4 s, 재방문 0.8 s, 나쁜 LTE 14 s)는 위 표로 대체한다.
   - 기준선은 서비스워커 요청에도 같은 스로틀을 걸었고, 회차 3번, 배포 etag 까지 기록했다.
   - 앞의 0.8 s 가 서비스워커 스로틀 없이 잰 값인지는 확인되지 않았다.

## 2. 원인 (측정 근거 포함)

### 원인 1 — v2 지형 타일 256장이 지구 화면 전체를 막는다 (가장 크다)
- **양**: 18.54 MB, 256건. 출처는 LH `network-requests` 이고, 직접 받아 잰 값도 18,345,644 B 다.
  - v2 첫 방문 30.77 MB 의 60 %다.
  - 로딩 화면이 걷히기 전에 받는 19.99 MB(기준선) 가운데 17.69 MB 가 지형이다.
- **막는 구조**: `v2-three/js/main.js:2306` 이 256장을 다 받을 때까지 `await` 한 뒤에야 지구 메시를 만든다(`:2394`).
  - 다른 시작 자료도 모두 기다린다. 나라 경계 `country-reference.json` 은 t≈11,343 ms, 지형이 끝난 뒤에야 출발한다(LH, 스로틀 없는 실측 시각).
  - 코드 주석의 의도는 반대다: `:2287` "직렬로 기다리면 첫 화면이 그만큼 늦다".
- **전달 경로**: 공개 서버 `s3.amazonaws.com/elevation-tiles-prod` 에서 받는다.
  - http/1.1 이라 호스트당 연결이 6개로 제한된다.
  - Cache-Control 이 없다(LH `cache-insight` 캐시 수명 0, curl 결과 `Last-Modified 2017-11-29` 만 있음).
  - 폰과 PC 가 같은 4단계를 받는다(`main.js:138-139`).
- **대역폭과 맞아떨어진다**: 나쁜 LTE 에서 20.96 MB ÷ 200 kB/s ≈ 105 s(계산)이고, 실측은 107.9 s 다.

### 원인 2 — 관측 구름 `clouds/global.png` 5.38 MB 를 v1·v2 모두 첫 화면에서 통째로 받는다
- 파일은 3072×1844 회색+알파 PNG, 5,381,747 B 다(S3 head-object).
  - 주석은 크기를 틀리게 적고 있다: `aws/gmgsi-clouds/handler.py:50` "약 2.5MB", `prototype/js/layers/imagery.js:261` "1.2MB".
- **v1**: 로딩 화면이 걷힌 뒤 15초 안에 8.7 MiB 를 더 받는다(기준선 실측, 11.08 − 2.38). 큰 것은 다음과 같다.
  - global.png 5.38 MB
  - 은하수 배경 4096 판 1.47 MB, 2048 판 0.31 MB
  - 나쁜 LTE 에서 로딩 화면(15.9 s)과 지구(25.4 s) 사이 약 9.5 s 가 검은 틈이다.
    - 이 틈에서 구름이 지구 타일과 대역폭을 다툰다는 것은 **추정**이다. 5.38 MB ÷ 200 kB/s ≈ 27 s 이지만 트레이스로 확인하지는 않았다.
- **v2**: 오하이오 S3 에서 직접 받는다(`v2-three/js/main.js:1476-1480`). 압축이 없고 폰·PC 판 구분도 없다.
- 받은 뒤 변환하는 CPU 도 무겁다(v1, 실측).
  - 긴 작업 497 ms(1,490→1,987 ms)가 있다.
  - `imagery.js:300-331` 이 화소마다 `Math.pow` 를 부르고 3072×1844 캔버스에 `toDataURL('image/png')` 를 두 번 한다.
  - 날씨 응답이 이 작업 뒤로 밀린다.

### 원인 3 — v1: Cesium.js 1.67 MB 가 동기 스크립트라 모든 것이 그 뒤로 줄을 선다
- 로딩 화면 전에 받는 2.38 MB 중 70 % 가 Cesium.js 다(기준선).
- 차단 지점은 `prototype/index.html:1249-1251` 의 동기 `<script src=…Cesium.js>` 다.
  - 파서가 여기서 막혀 `<script type=module>`(`:1257`)에 늦게 닿는다.
  - 그래서 2단 모듈 요청이 394 ms 에야 나간다(LH 실측 시각).
- 정적 import 가 4단(1·37·51·19개, 108개)이다(`build/perf-investigation/v1-modgraph.json`).
  - 문서까지 합쳐 5번을 차례로 왕복한다.
  - 재방문 계산 `5 × (LTE 왕복 70~150 ms + 엣지 확인 34 ms)` = 0.52~0.92 s 로, 실측 0.85 s 를 재현한다(캐시 보고서의 식).
- 나쁜 LTE 첫 방문은 대역폭이 병목이다. 캐시를 바꿔도 첫 방문 효과는 거의 0 이다(캐시 보고서). 줄일 것은 바이트다.
- `unused-javascript` 는 Cesium 1,667 KB 중 824 KB 가 안 쓰인다고 한다. 그러나 빌드 없이 배포하는 규칙(HANDOVER §3) 때문에 잘라낼 수 없다.

### 원인 4 — v2 자료를 CloudFront 를 거치지 않고 오하이오 S3 에서 직접 받는다
- 주소가 14개 이상 파일에 하드코딩돼 있다. 예: `engine-bridge.js:435`, `live-layers.js:23`, `gfs-frames.js:63`, `grid-frames.js:69`, `intel-feed.js:12-30`.
- S3 는 압축하지 않는다. 오하이오까지 왕복은 188 ms 다(LH network-rtt).
- 예: 구름 높이 `clouds/gk2a/cth/grid.json`(curl 실측)
  - S3 직접: 1,867,169 B, 2.0 s
  - earthus.net 경유: br 541,523 B, 0.56 s
- `grid.json` 자체도 크다.
  - `aws/gk2a-clouds/cth_pipeline.py:377-378` 의 `np.round(lon,5)` 가 float32 에 걸려 반올림 효과가 없다. 그래서 17자리 숫자가 나간다.
  - ⚠️ 운영에서 이 파일을 실제로 쓰는 진입점이 `cth_pipeline.py` 인지, `combined_handler.py`·`cth_pipeline_lcc.py` 인지는 **확인하지 못했다**.
- v1 은 이 문제를 이미 풀었다: `prototype/js/config.js:20-33` 이 같은 출처·brotli·한국 엣지를 쓴다. v2 로 옮겨지지 않았을 뿐이다.

### 원인 5 — v1 첫 방문 폰: 위치 권한 창에 답하기 전까지 시계·날짜·온도가 비어 있다 (측정 도구에는 안 잡힌다)
- 시계를 그리는 `tick()`(`prototype/js/ui.js:63`)이 위치 대기(`ui.js:55` `await locateUser()`) 뒤에 있다.
- 그리고 `main.js:494` 가 `await chrome.init()` 으로 그 전체를 기다린다.
- 명세상 권한 창이 떠 있는 동안에는 8초 제한(`mylocation.js:53`)이 흐르지 않는다.
- 그래서 `main.js:495` 이후 초기화(계정·출처·특보)도 같이 멈춘다.
- Lighthouse 는 권한을 즉시 거부하므로 점수에 나타나지 않는다. `geolocation-on-start` 점수는 0 이다.

## 5. 되돌리는 법 · 다시 재는 법

### 되돌리기
- **코드 변경(바로 할 것들)**: 해당 커밋을 되돌리고 같은 배포 절차로 다시 올린다. 새 자산(지형 한 장, WebP 변형)은 옛 파일을 지우지 않고 **나란히** 두므로, 코드만 되돌리면 옛 경로로 돌아간다.
  - earthus-deploy 는 삭제 권한이 없다(`aws/deploy-app.sh:42-45`). 옛 파일은 어차피 남는다.
- **헤더만 되돌릴 때**
  - v2: 예전 `cache_control()` 로 `FORCE_UPLOAD=1` 재업로드(`deploy-v2-three.sh:111-113`).
  - v1: 키마다 제자리 복사 `--metadata-directive REPLACE --cache-control no-cache`(`deploy-app.sh:62-66` 패턴) + `/*` 무효화.
- **v2 해시 번들**: 이전 커밋의 index.html 만 다시 올리고 `/v2/` 키를 무효화한다. 옛 해시 파일이 S3 에 남아 있어 즉시·정확히 돌아간다.
- **서비스워커**: 이전 sw.js 를 올린다(no-cache). `skipWaiting + clients.claim`(`sw.js:53·78`)이라 다음 화면 이동 때 바로 교체된다. 비상시에는 스스로 등록을 해제하는 sw.js 를 올린다.
- **유일한 비가역 위험**: 내용이 바뀔 수 있는 URL 에 `immutable` 을 거는 것이다. 브라우저 캐시는 무효화가 닿지 않아 최대 1년 갇힌다. 그래서 immutable 은 내용 해시 파일 이름에만, 덮어쓰기 검사와 함께 건다.
- ⚠️ 배포 스크립트를 "확인용"으로 실행하지 않는다. 2026-09-23 에 가드 통과로 운영에 29개가 나간 적이 있다. 시험은 `bash -n` 과 함수 source 로만 한다.

### 다시 재기
```
node build/perf-investigation/lte-baseline.mjs --runs=2 --runs-lte=3
#   일부만:  --only=v2-lte,v2-poor
#   서비스워커 요청도 같은 스로틀(기본):  --sw=throttle
```
- **새 배포를 잰 것인지 확인한다.** 결과의 문서 etag 가 기준선과 달라야 한다. 기준선은 v1 `W/"903e3404…"`, v2 `W/"342e54b6…"` 다.
- **오염 회차는 버린다.** 회차별 `hostCpuPct`·`longTaskMsToLoader` 가 높은 회차를 뺀다(오늘 v2 LTE r1·r2 사례).
- **비교할 열**: v1 은 loader·globe·LCP(`#ambTemp`). v2 는 **loader·globe** 로 보고, LCP(로고)는 보지 않는다.
- Lighthouse 는 보조로만 쓴다: `build/ux-check/<시각>/lighthouse-v1.json`, `lighthouse-v2.json` 의 `total-byte-weight`·`network-requests`·`bootup-time`. 모의 LCP 는 목표로 쓰지 않는다.
- **목표(제안)**: v2 LTE 첫 방문 loader 21.5 s → **6~9 s** (V2-1 적용 후 바이트 하한 약 5.5 s ~ 단순 차감 약 8 s, 추정). 6 s 이하는 V2-2 까지 해야 닿는 도전 목표다.
- 설명되지 않은 이상치: 시험 중 v1 LTE 재방문이 9.4 s·23.3 s 로 나온 적이 두 번 있다. 본 실행에서는 다시 나오지 않았다. 다시 나오면 따로 추적한다.
