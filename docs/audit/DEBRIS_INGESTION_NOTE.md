# 우주쓰레기 수집 — GROUP 경로 도입 기록

> 2026-09-01 · PD 지시("우주쓰레기 잘 붙혀야해") 이행 기록

## 왜 GROUP 경로를 새로 만들었나

기존 수집 API는 `CATNR` 단일 조회뿐이었다. 파편운은 한 가족이 수백~수천 기라
개별 조회로 붙이면 (1) CelesTrak 이용 지침 위반 수준의 요청 폭주, (2) 파편마다
다른 raw 아티팩트가 생겨 **계보 뿌리가 흩어진다**. 그래서 문서화된 `GROUP` 질의를
쓰는 경로를 추가했다: **한 가족 = 한 요청 = 한 불변 아티팩트 = 한 SHA-256 뿌리**.

## 수집 결과 (라이브, CelesTrak 공식 궤도요소)

카탈로그 총계: 객체 2,689 · 궤도해 3,081 · raw 아티팩트 501.

## 정직성 규칙 (구현·검증됨)

- 모든 멤버가 **동일 raw 아티팩트**를 참조 (테스트: 이번 런의 solution id로 범위 한정 후 DISTINCT 검사)
- 불량 행은 조용히 버리지 않고 **사유와 함께 격리**(`ingestion_record_rejection`) + 응답에 `rejection_reasons` 집계
- 쓸 수 있는 행이 하나도 없으면 **레코드를 만들지 않고** `INSUFFICIENT_DATA`
- 그룹 슬러그는 화이트리스트 정규식으로 검증 (임의 질의 주입 차단)
- GP/OMM에는 공분산이 없으므로 Pc는 `NOT_COMPUTED` 유지 — 파편이 많아져도 이 규칙은 불변

## 지구 레이어 반영

`prototype/v2-three/js/aetherus-link.js`가 서버 커버리지를 읽어 **절단 사실을 화면에 적는다**:
"정본 카탈로그 2,689기 중 500기만 표시 — 서버 페이지 상한입니다. 자른 만큼 여기에 적습니다."
표시분 중 파편·로켓바디 수와 출처 파편운도 카드에 명시. (1.0 원칙: 자르면 반드시 화면에 적는다)

## 성능: 측정과 조치 (2026-09-01)

실제 파편 규모를 붙이자 전 카탈로그 스크리닝이 느려졌다. 추측 대신 단계별로 측정했다
(1,998 객체 · 6시간 창 · 30초 그리드):

| 단계 | 시간 | 관찰 |
| --- | --- | --- |
| SGP4 전파 (벡터화) | 0.2s | 1998×721 그리드가 이미 충분히 빠름 |
| 셸(반경 포락) 필터 | 0.1s | **200만 쌍 중 180만 생존 — 10%만 제거** |
| **레벨1 표본거리 스캔** | **~99s** | 병목 |
| 레벨2 정밀화 | ~18s | 38만 생존쌍 |

**근본 원인**: 파편운은 정의상 같은 파괴 사건에서 나와 **거의 동일한 셸에 뭉쳐 있다**.
반경 포락 필터는 서로 다른 고도의 쌍만 쳐내므로 파편 대 파편에는 거의 무력하다.
알고리즘 결함이 아니라 실제 파편 분포의 성질이다.

**조치 — 알고리즘 불변, 병렬화만**: 레벨1은 청크가 완전히 독립적이고 시간 대부분을
NumPy(GIL 해제) 안에서 쓴다. `ThreadPoolExecutor`로 청크를 나눠 처리하되 `map`이
순서를 보존하므로 후보 순서·해시가 순차 경로와 **바이트 단위로 동일**하다.
보수적 필터 체인(false-negative=0 보장)은 한 줄도 건드리지 않았다.

- 검증: 순차 99.2s / 병렬 35.9s → **2.8배**, 후보 48,678건 **완전 동일**
- 워커 수는 `AETHERUS_SCREENING_WORKERS`로 고정 가능(기본: CPU-1, 최대 8, 청크 4개 미만이면 순차)

**남은 선택지**(추가 개선이 필요해질 때): 시간축 계층적 프리필터, 셸별 분할 실행,
또는 P10 벤치마크 러너로 예산 고정. 현재 규모에서는 병렬화로 실용 범위에 들어왔다.
