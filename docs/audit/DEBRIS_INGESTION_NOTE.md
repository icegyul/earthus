# 우주쓰레기 수집 — GROUP 경로 도입 기록

> 2026-09-01 · PD 지시("우주쓰레기 잘 붙혀야해") 이행 기록

## 왜 GROUP 경로를 새로 만들었나

기존 수집 API는 `CATNR` 단일 조회뿐이었다. 파편운은 한 가족이 수백~수천 기라
개별 조회로 붙이면 (1) CelesTrak 이용 지침 위반 수준의 요청 폭주, (2) 파편마다
다른 raw 아티팩트가 생겨 **계보 뿌리가 흩어진다**. 그래서 문서화된 `GROUP` 질의를
쓰는 경로를 추가했다: **한 가족 = 한 요청 = 한 불변 아티팩트 = 한 SHA-256 뿌리**.

카탈로그 총계: 객체 2,689 · 궤도해 3,081 · raw 아티팩트 501.

## 정직성 규칙 (구현·검증됨)

- 모든 멤버가 **동일 raw 아티팩트**를 참조 (테스트: 이번 런의 solution id로 범위 한정 후 DISTINCT 검사)
- 불량 행은 조용히 버리지 않고 **사유와 함께 격리**(`ingestion_record_rejection`) + 응답에 `rejection_reasons` 집계
- 쓸 수 있는 행이 하나도 없으면 **레코드를 만들지 않고** `INSUFFICIENT_DATA`
- 그룹 슬러그는 화이트리스트 정규식으로 검증 (임의 질의 주입 차단)
- GP/OMM에는 공분산이 없으므로 Pc는 `NOT_COMPUTED` 유지 — 파편이 많아져도 이 규칙은 불변

## 지구 레이어 반영

`prototype/v2-three/js/aetherus-link.js`가 서버 커버리지를 읽어 **절단 사실을 화면에 적는다**:
"정본 카탈로그 2,689기 중 500기만 표시 — 서버 페이지 상한입니다. 자른 만큼 여기에 적습니다."
표시분 중 파편·로켓바디 수와 출처 파편운도 카드에 명시. (1.0 원칙: 자르면 반드시 화면에 적는다)

## 성능 소견 (후속 과제)

카탈로그가 6기 → 2,689기가 되면서 전 카탈로그 스크리닝이 O(n²)로 커졌다
(`screening_max_objects=2000` → 약 200만 쌍). 기능은 정상이나 전 구간 테스트
시간이 크게 늘었다. 후속 선택지: 셸/고도 사전 분할(이미 shell_margin 필터 존재),
스크리닝 대상 부분집합 파라미터, 또는 P10 벤치마크 러너로 예산 고정.
**이 소견은 실제 파편 규모를 붙였기 때문에 처음 관측된 것이다.**
