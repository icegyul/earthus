## 배경 — 로드맵 질문이 결함 조사로 바뀐 경위

"공개 데이터만으로 Pc 대안을 어떻게 마련할 것인가"를 검토하던 중, 유력 후보였던
**CelesTrak SOCRATES MAX_PROB 수집이 잠복 결함의 방아쇠**임이 드러났다. 즉
권고안 자체가 결함을 발화시키는 순서였다. 착수 순서를 바꾸고 결함을 먼저 고쳤다.

## 결함 1 — MAX_PC 상태를 값의 존재로부터 추론 (계보 위조)

`backend/conjunction/service.py:589` (수정 전):

```python
"status": "COMPUTED" if row["max_pc"] is not None else "NOT_COMPUTED"
```

바로 네 줄 위 PC 채널은 저장된 `pc_status`를 그대로 통과시킨다(`service.py:580-585`).
MAX_PC 만 추론했고, 그 추론은 언제나 **우리에게 유리한 방향**이었다.

원인은 스키마다. `migrations/001_initial_schema.sql:144-145` 가 `max_pc`, `max_pc_method`
는 주었으나 `max_pc_status` 는 주지 않았다. 없는 컬럼을 코드가 메웠다.

**발화 조건**: 외부 스크리닝 지표가 컬럼에 들어오는 순간. 제3자가 계산해 공표한 값이
"Aetherus가 계산함"으로 모든 API 클라이언트에 보고된다. 절대규칙 *계보 보존* 위반.

**당시 실측**: `max_pc IS NOT NULL` **0건**, `pc_status='COMPUTED'` **0건**
(NOT_COMPUTED 44,858 / NULL 30). 잠복이었고 아직 발화하지 않았다.

### 조치

`migrations/016_max_pc_basis.sql`:

| 컬럼 | 뜻 |
| --- | --- |
| `max_pc_basis` | `COMPUTED_INTERNAL` / `OBSERVED_EXTERNAL` / `ASSUMED_FAMILY` |
| `max_pc_status` | `COMPUTED` / `OBSERVED` / `ASSUMED` / `NOT_COMPUTED` / `BASIS_UNRECORDED` |
| `max_pc_artifact_id` | 값을 실어온 원본 아티팩트 (궤도해 아티팩트와 별개일 수 있음) |

DB 제약 4건이 최종 방어선이다. 값이 있으면 근거가 있어야 하고(`needs_basis`),
외부 관측값은 아티팩트가 있어야 한다(`needs_artifact`).

코드(`_max_pc_channel`)는 저장 상태를 통과시키되, **근거와 모순되는 저장 상태는
따르지 않는다** — `COMPUTED` 는 `COMPUTED_INTERNAL` 일 때만 허용된다.

### 부수 발견 — append-only 트리거가 옳았다

기존 행을 `max_pc_status='NOT_COMPUTED'` 로 백필하려 했으나 트리거가 거부했다:

```
conjunction_snapshot is append-only; refreshes must INSERT a new snapshot
```

**트리거를 우회하지 않았다.** 과학 기록을 사후에 고쳐 쓰는 것은 이 프로젝트가
막으려는 바로 그 행위다. 백필은 불필요하기도 했다 — 기존 행의 `max_pc` 가 전부
NULL 이므로 소급 판정할 값 자체가 없다.

## 결함 2 — 부재 채널이 0.0 으로 취급되어 이득이 날조됨 (특허 청구항 직하)

`backend/benefit/models.py:183` (수정 전)의 `object_risk` 는 맨 `sum()` 이라
해당 채널 간선이 하나도 없으면 **0.0** 을 반환했다. `backend/benefit/graph.py:335-337`
은 그 값을 조건 없이 뺐다.

두 그래프가 같은 경로로 만들어지는 동안은 안전하다. 그러나 실제로는 다르다 —
`backend/benefit/physical.py:327-331` 은 물리 재계산 반사실 행마다 `pc`/`max_pc` 를
None 으로 고정한다(그 자체는 정직하며 `COVARIANCE_MISSING_PUBLIC_GP` 사유까지 남긴다).

따라서 기준선에 실제 PC 간선이 하나라도 생기면:

```
benefit = 실제값 − 0.0 = 실제값 전량
```

이 값이 **"이 파편을 제거하면 충돌확률이 이만큼 사라진다"** 로 공표된다.
개입이 만들지 않은 변화를 개입에 귀속하는 것이며, 절대규칙 *없는 데이터는
UNAVAILABLE, 결코 0 아님* 위반이다. 위치가 특허 청구항 바로 아래다.

### 조치

#### 첫 시도는 틀렸다 — 판별 기준을 정정했다

처음에는 `object_risk` 가 채널 부재 시 `None` 을 반환하게 하고, 두 그래프 중
한쪽에만 있는 채널은 빼지 않도록 했다. **이것이 정당한 이득까지 막았다.**

`test_ben001_direct_benefit_and_provenance` 가 `KeyError: 'PC'` 로 실패하며 드러났다.
그 시나리오에서 반사실에 PC 간선이 없는 이유는 **개입이 그것을 지웠기 때문**이다.
제거된 물체가 유일한 PC 간선을 들고 있었다면, 제거는 실제로 그 위험을 없앤 것이고
전액 이득이 **정답**이다. 테스트가 옳았고 내 판별자가 두 경우를 뭉갰다:

| | 반사실에 채널이 없는 이유 | 올바른 처리 |
| --- | --- | --- |
| **(a)** | 재계산 경로가 그 채널을 **애초에 만들 수 없음** | 비교 불가 → INSUFFICIENT_DATA |
| **(b)** | **개입이 그 간선들을 지움** | 전액 이득 (정답) |

관측이 아니라 **능력**으로 판별해야 한다. 간선 삭제(IDEALIZED)는 Gs 를 G0 에서
파생시키므로 모든 부재가 개입의 결과다. 물리 재계산은 공분산 없는 공개 GP 를
전파하므로 **구조적으로 PC·MAX_PC 를 만들 수 없다** — 여기서만 결함이다.

#### 최종 조치

- `RiskGraph.has_channel()` / `channels()` 신설
- `object_risk` 는 그대로 `float` — 간선을 잃은 객체의 0.0 은 **측정된 결과**다
- `PHYSICAL_RECOMPUTE_CHANNELS = frozenset({"CONJUNCTION_EXPOSURE"})` — 물리 경로가
  무엇을 만들 수 있는지 코드에 선언
- `attribute_direct_beneficiaries(..., counterfactual_channels=None)` —
  `None` 이면 간선 삭제 의미(기준선 채널과 동일), 물리 경로는 위 집합을 넘긴다
- `channel_parity_warnings(..., counterfactual_channels)` 가 거부 사유를 기록 →
  실행의 `warnings_json` 에 적재
- `backend/benefit/protect.py` 의 뺄셈 3곳은 `comparable_metrics()` 로 필터하고,
  `excluded_metrics` 를 결과에 **빈 리스트일 때도 실어** 조용한 누락과 구분한다

판별을 `object_risk` 에서 귀속 계층으로 옮긴 것이 핵심이다. 0.0 이 의미 있는지는
반사실이 **어떻게 만들어졌는지** 알아야 답할 수 있고, 그 정보는 두 그래프가 만나는
지점에만 있다.

## 결함 3 — Pc 엔진 검증이 자기순환

`tests/fixtures/cdm/tracss_spec_example_cdm_valid.json` 은 자신의 note 에
*"6x6 공분산 행렬은 이 픽스처를 위해 구성한 합성 검증값"* 이라고 적어두었다.
정직하게 밝힌 것은 잘한 일이다. 문제는 **그것이 무엇을 증명하는가**이다.

이 픽스처는 JSON · 6x6 중첩 · TEME · km2 — **우리 파서와 Pc 게이트가 요구하는
바로 그 규약**이다. Pc 엔진이 통과시킨 유일한 공분산은 엔진에 맞춰 만든 것이었다.

### 실측 — 규격 형태 문서는 5개 관문에서 죽는다

`tests/fixtures/cdm/ccsds_508_kvn_shaped.txt` (CCSDS 508.0-B-1 **구조**로 구성,
수치는 무의미)를 실제로 통과시켜 기록했다:

| # | 관문 | 우리 요구 | 실제 CDM | 근거 |
| --- | --- | --- | --- | --- |
| 1 | 인코딩 | JSON | **KVN 또는 XML** | `cdm.py:61` |
| 2 | 공분산 형태 | 6×6 중첩 리스트 | 21원소 하삼각 | `cdm.py:25` |
| 3 | 프레임 | `TEME` | **RTN** | `pc.py:72` |
| 4 | 단위 | `KM2` | **m\*\*2** | `pc.py:22` |
| 5 | HBR 의미 | `COMBINED_HBR` | 규격 외 전달 | `pc.py:154` |

관문 3·4 는 `covariance_check` 를 직접 호출해 거부를 확인했다(관문 1이 파서 진입을
막으므로). **필요한 정보는 문서에 다 있다** — 읽지 못하는 것이 우리 문제다.

### 조치

- 기존 픽스처에 `shape_class: ENGINE_SHAPED` 명시 — 후속 독자가 규격 증거로 오인하지 않도록
- `tests/unit/test_cdm_spec_shape_reality.py` 9건: **현재 동작을 그대로 기록**한다.
  희망사항이 아니라 격차의 지도다. 격차가 메워지면 이 테스트들이 실패하며, 그것이 신호다.
- 자기순환 부재 불변식 명문화: 외부 문서에서 온(`source_uri` + `content_sha256`)
  Pc 골든 픽스처가 **하나도 없다**. 이 부재가 관문 3·4 를 오래 가린 이유다.

## 판정에 미치는 영향

## 결함 4 — 2차 비용이 테스트와 API 양쪽을 멈추게 하고 있었다

우주쓰레기 2,851개를 넣으면서 근접 스크리닝 쌍이 약 200만으로 늘었다. 쌍 수는
모집단의 **제곱**으로 증가하는데, 호출부 어디에도 모집단을 한정할 방법이 없었다.

### 실측 (2026-09-02)

| 모집단 | 쌍 | 소요 | 이벤트 |
| --- | --- | --- | --- |
| 6객체 (범위 지정) | 6 | **0.01s** | — |
| 150객체 | 10,878 | **11.5s** | 12 |
| 400객체 | 79,003 | 100.4s | 98 |
| 800객체 | — | 400s 초과 | — |
| 전 카탈로그 | 약 2,000,000 | 약 40분 | — |

2.7배 모집단이 8.7배 시간(2.7²=7.2에 근접) — 2차 증가가 그대로 확인된다.

### 파급 1 — 테스트

P5/P6 테스트는 6객체 합성 코퍼스를 심어놓고 **전 카탈로그를 스크리닝한 뒤 결과에서
자기 코퍼스만 골라냈다**(`test_p5_physical_counterfactual.py:137-138`). 전체를 계산할
이유가 없었다.

`test_conjunctions_api.py` 의 `_screened_once` 는 **함수 스코프**여서 10개 테스트마다
전 카탈로그를 다시 돌렸다.

### 파급 2 — 운영 API (이쪽이 더 중요하다)

`backend/main.py` 의 `POST /v1/conjunctions/screen-runs` docstring 은 이렇게 적고 있었다:

> *"실제 저장 카탈로그는 설정으로 제한되므로 이 라우트는 동기 실행한다"*

**우주쓰레기 수집이 이 전제를 깼다.** 202를 반환하면서 실제로는 수십 분간 워커를
점유한다. 테스트 지연이 아니라 운영 결함이었고, 테스트가 그것을 드러냈다.

### 조치

- `load_screenable_solutions(max_objects, catalog_ids=None)` — 모집단을 명시 집합으로 한정
- `run_screening(..., catalog_ids=None, max_objects=None)` — 집합 지정과 개수 상한을 분리
  (호출자가 어떤 객체인지는 몰라도 얼마나 감당할 수 있는지는 아는 경우가 있다)
- 응답의 `coverage` 블록이 `FULL_CATALOGUE` / `CATALOG_SUBSET` 을 기록한다 —
  **부분 스크리닝 결과가 전 카탈로그 커버리지로 오독되면 안 된다**
- `screen-runs` 엔드포인트에 `max_objects` 질의 파라미터 추가 (기본값 불변, 하위 호환)
- Benefit 반사실 재계산 3곳에 `catalog_scope` 배선

**건전성 조건을 코드에 명시했다**: REMOVE 는 물체를 지울 뿐이라 간선을 만들 수 없으므로
기준선 모집단을 덮는 범위면 충분하다. 그러나 **SUBSTITUTE·OCM 은 물체를 새 궤도로 옮겨
범위 밖 객체와 새 간선을 만들 수 있다** — 그런 실행에 범위를 좁히면 기동이 새로 만든
위험을 PROTECT 가 과소보고한다. 보장할 수 없는 호출자는 None 을 넘겨 전 카탈로그를 쓴다.

### 부수 효과 — 테스트 격리

기존 P5/P6 는 **개발 DB 에 무엇이 들어있느냐에 따라 결과가 달라졌다**. 통과해도 의미가
약했다는 뜻이다. 범위 지정으로 자기 코퍼스만 보게 되어 격리가 확보됐다.

`test_conjunctions_api.py` 는 모듈 스코프 + 150객체로 바꾸되, 픽스처가 **이벤트가 실제로
생성됐는지 단언**한다. 여러 테스트가 이벤트를 순회하는데 이벤트가 0이면 루프가 공회전하며
조용히 통과하기 때문이다.

### 프레임 회전을 하지 않은 이유

CDM 공분산은 RTN 이고, TEME 로 회전하려면 **물체 상태벡터와 정확한 축 규약**이 필요하다.
여기서의 오류는 **조용하다** — 실패로 드러나지 않고 그럴듯한 Pc 값을 만든다.
E43(하드코딩 84%)·E10(날조된 밀도 기본값)과 같은 실패 유형이다.

그래서 프레임을 **공표된 그대로 RTN 으로 보고**하고 Pc 게이트가 계속 거부하게 뒀다.
`covariance_summary()` 가 남은 차단 요인을 열거한다. 회전은 검토를 거쳐 별도로 다룰
작업이며, 밤중에 무감독으로 넣을 물리가 아니다.

### 단위 변환에서 주의한 것

CDM 하삼각은 위치(m\*\*2)·위치×속도(m\*\*2/s)·속도(m\*\*2/s\*\*2)를 **섞어** 싣는다.
행렬 전체에 1e-6 을 곱하면 속도 블록이 망가진다. **3×3 위치 블록만 변환**하고
나머지는 공표 단위 그대로 통과시키며, 그 사실을 경고로 남긴다.

불완전한 하삼각(21개 미만)은 **0으로 채우지 않고 부재로 처리**한다. 0 으로 채우면
Pc 엔진에 "완벽히 확실한 상태벡터"를 넘기게 된다.

### 새로 드러난 사실 — 파서에 운영 호출부가 없다

`parse_cdm` / `parse_any_cdm` 을 호출하는 라우트·서비스·수집 작업이 **하나도 없다**.
CDM 을 읽을 수 있다는 것과 수집한다는 것은 별개의 주장이며, 여기서는 첫 번째만 성립한다.
`test_cdm_spec_shape_reality.py::TestNoIngestionPathExists` 가 이 사실을 검사하고,
호출부가 생기면 실패하며 그때 은퇴시켜야 한다.

### 검증

- KVN 파서 25건 + 갱신된 현실성 11건 = **36건**
- 현실성 테스트는 여전히 **현재 동작을 기록**한다. 프레임 관문이 열리면 실패하며,

```

→ 4건 모두: MAX_PC status=OBSERVED · basis=OBSERVED_EXTERNAL
```

### 수집 중 만난 관문 두 개 (설계가 의도대로 작동)

1. **출처 레지스트리 FK 거부** — `raw_artifact.source_id → data_source` FK 가
   미등록 출처의 첫 저장을 거부했다. 우회 대신 `017_register_socrates_source` 로
   정식 등록했다(이용정책·36000초 폴링 한도 명시). E27 교정과 같은 원칙:
   신뢰는 사전 구성 레지스트리에서만 나온다.
2. **HTTP 406** — 공용 클라이언트가 `Accept: application/json` 을 고정 전송했고
   CelesTrak 이 CSV 자원에 406 을 반환했다. 정책대로 재시도 없이 즉시 중단됐고,
   `fetch_raw(accept=...)` 파라미터로 교정 후 의도적 1회 재요청으로 성공했다.
   픽스처로는 절대 못 잡는 종류의 결함이다.

**조치** — `migrations/018_geometry_basis.sql`: `geometry_basis`
(`COMPUTED_INTERNAL` / `OBSERVED_EXTERNAL`). 스크리닝 경로는 INTERNAL, SOCRATES 는

**018 이전 행의 처리** — append-only 라 백필 불가. 근거 컬럼이 NULL 인 행은

## 후속 5 — REMOVE 한정 관측 MAX_PC 이월 (Benefit 이 관측값을 소비하기 시작)

물리 재계산은 공분산 없는 공개 GP 를 전파하므로 MAX_PC 를 만들 수 없고, 대칭성
가드는 그 채널의 뺄셈을 거부해 왔다. 이월 규칙이 **정확히 한 가지 개입**에 한해
채널을 연다:

> REMOVE 는 다른 어떤 쌍의 궤도도 바꾸지 못한다. 따라서 제3자가 공표한, 건드리지
> 않은 쌍의 스크리닝 상한은 Gs 에서도 G0 에서와 똑같이 유효하다. 제거된 물체의
> 쌍에 걸린 상한은 소멸하며, **그 소멸이 곧 관측된 이득이다.**

SUBSTITUTE/OCM 은 이월하지 않는다 — 물체를 옮기면 공표자의 옛 상한은 무효가 되고
새 쌍은 공표자가 스크리닝한 적이 없다. `evaluate_ocm_candidate` 는 재계산 전용
능력 집합을 유지한다.

### 구현 (`backend/benefit/physical.py`)

- `carry_into_baseline` / `carry_into_scenario` / `carry_forward_observed_max_pc`
- 모든 이월 간선은 provenance 에 `carried_forward: true`, `carry_method:
  CARRIED_FORWARD_OBSERVED_V1`, 규칙 전문, 출처 기준선 id 를 실어 영속된다 —
  **값은 옮겨질 뿐 재계산되지 않는다**
- 능력 집합 `REMOVE_CARRYFORWARD_CHANNELS = 재계산 채널 ∪ {MAX_PC}` 는 REMOVE
  경로(시나리오·PROTECT 랭킹)에만 전달되고, 실행 경고 `MAX_PC_CARRIED_FORWARD` 가
  이월·소멸 계수를 기록한다

### 원장 오염 함정 (구현 중 설계로 회피)

이월 간선을 `derive_candidate` 에 넘기는 G0′ 에 미리 넣으면, 재계산 Gs 에 없는
MAX_PC 간선들이 **모든 후보에서 "제거됨"으로 위조**된다. 그래서 원장은 순정
그래프로 계산하고 이월은 그 뒤에 얹으며, 제거 대상에 걸린 이월 간선만 원장에
소멸 델타로 추가한다. PROTECT 후보 선정은 이월 반영 그래프(neighbors)를 쓴다 —
공표자가 관측한 이웃도 정당한 제거 후보이기 때문이다.

검증: 이월 단위 9건 — 값 이동 불변·표식·소멸 원장·이월 후 대칭성 가드 통과·
능력 집합 없이는 여전히 거부. 전 단위/계약/기반 402 통과.

결함 5 의 픽스처 231건 삭제는 이로써 **필요 없어졌다** — 정책이 시뮬레이션 등급을
기본에서 제외하고 테스트가 더는 그 부재를 가정하지 않는다. 삭제는 보류 유지.

### 마감 중 겪은 충돌 — 증거 생성과 회귀를 같은 DB 에서 병렬로 돌리면 안 된다

전체 회귀와 p8 증거 재생성을 동시에 실행했더니 둘 다 P5 기준선 버전 관리 테스트가
`605 == 601 + 2` 로 실패했다 — 한쪽이 세는 사이 다른 쪽이 기준선 2개를 추가한 것이다.
같은 테스트를 **단독으로 다시 돌리면 4/4 통과**한다. 코드 결함이 아니라 실행 규율의
문제이며, 결함 5·7 과 뿌리가 같다: 통합 테스트와 증거 생성기는 공유 개발 DB 의
**내용뿐 아니라 동시성도** 가정한다.

규칙으로 남긴다: 증거 생성기(특히 P5/P6 스위트를 내장한 p8)는 다른 스위트가 도는
동안 실행하지 않는다. 증거 파일의 `tests_p5_pass` 가 False 인데 단독 실행이 통과하면
가장 먼저 의심할 것은 동시 실행이다.

### 커밋 경계 혼입 (기록)

다른 챗이 같은 저장소에서 동시에 작업하는 동안, 내가 `git add` 로 스테이징해둔
23개 파일이 그쪽 커밋 `70366d4e` 에 함께 들어갔다. **작업 손실은 없다** —
내용을 확인했고 전부 온전하며 작업 트리도 깨끗하다. 다만 커밋 경계가 섞여
`70366d4e` 는 지구 렌더링 작업과 CDM 준비 계층·비동기 잡·수집 원자성이 한
커밋에 들어 있다.

원인은 내 실행 규율이다: 스테이징한 채로 오래 두면 다른 작업자의 `git commit` 이
그것을 가져간다. 공유 저장소에서는 **스테이징과 커밋 사이를 벌리지 않는 것**이
규칙이어야 한다. (동시성이 문제를 만든 세 번째 사례 — 결함 5·7, 증거 생성 충돌에
이어서.)

### 정직성 제약 (연결하면서 지킨 것)

- **E16 은 데이터를 만들지 않는다.** 경로만 생겼고 부재는 부재로 남는다. 단위 계약도
  엔진이 강제한다(km 아닌 altitude 는 422).
- **E15 는 전이를 발명하지 않는다.** 공식 전이는 증거 없이는 거부되고, 불법 전이는
  상태기계가 막는다. 이력이 비면 "전이가 기록되지 않았다"고 말한다.
- **E44 importance 는 입력이 없으면 점수를 내지 않는다.** 없는 입력의 **이름을 응답에
  넣고** INSUFFICIENT_DATA 를 반환한다 — 기본값으로 대체하면 도출된 것처럼 보이는
  가중 점수가 나오기 때문이다(E43 하드코딩 84% 와 같은 실패 유형).
- **E44 decision 은 실행되지 않은 시나리오를 비교하지 않는다.** 저장된 실행만 옵션이
  되고, 새 위험은 감점으로 드러나며, 명령 형태 필드는 제거되고
  `NO_AUTOMATIC_SPACECRAFT_COMMAND` 가 찍힌다.

### 정정한 두 가지 (에이전트 조사 결과 중)

1. **E39 는 죽어 있지 않다.** `packet.py:47` 이 생성하고 `:97` 이 실제로 `fuse()` 를
   호출한다. 죽은 것은 `advanced.py` 의 **중복 사본**이며, 그것을 연결하면 살아있는
   경로가 둘이 되어 더 나빠진다. 연결 대상에서 제외했다.
2. **`/v1` 반사실이 지시서 금지 사항을 서빙한다는 지적은 과했다.** 그 경로는
   `VAL-A/B/C` 픽스처만 받아 실객체를 거부하고, 엔진·저장·응답 세 층에서
   `RESEARCH_ONLY` 로 라벨되며 "관측된 이득이 아님" 경고가 붙는다. 지시서가 금지한
   것은 간선 삭제를 **P5 결과라고 부르는 것**인데 이 경로는 그렇게 주장하지 않는다.
   진짜 격차는 더 온건하다: **P5 준수 엔진이 `/api/v1` 에만 있고 제품 표면에 연결되지
   않았다**는 통합 문제다. (별도 작업)

검증: 신설 통합 17건. 각 엔진이 실제 호출되는 것과, 연결이 데이터를 만들지 않은 것을
양쪽 다 단언한다.

**LLM 계층(L01~L08)은 PD 지시로 대기.** 공급자가 없어 L01 의 유일한 구현이 프롬프트를
그대로 반환하는 상태이며, 이는 별도 판단 사항이다.

### E10 — 엔진의 거절이 클라이언트에 닿지 않고 있었다

Kp·X-ray 라우트가 프로바이더 페이로드를 직행시켜 E10 이 실행되지 않았고, 그 결과
**"명명된 대기밀도 모델이 연결돼 있지 않으므로 density_factor 를 산출하지 않는다"**는
E10 의 핵심 진술이 응답에 없었다. 값이 그냥 오늘 빠진 것처럼 읽힌다. `drag-context`

### E11 — 등급→검증상태 매핑이 통째로 빠져 있었다

NEO 라우트가 프로바이더 행을 손대지 않고 반환해, 출처 등급을 검증 상태로 매핑하고

`normalized` 블록을 붙이고 `normalized_by: E11` 을 찍는다.

### E39~E43 — 추적성 문제였지 기능 문제가 아니었다

살아서 도는 구현(`SignalPromotionGate`·`EventCorrelator`·`RevisionBuilder`·
`ConfidenceEngine`·`UncertaintyEngine`, 그리고 패킷 빌더의 fusion)에 **엔진 id 가 하나도
선언돼 있지 않았고**, id 를 가진 `advanced.py` 사본은 런타임에서 생성만 되고 호출부가
0건이었다. 즉 **능력은 도달 가능한데 식별자는 죽은 코드를 가리키고** 있었다.

id 를 실제로 도는 구현에 붙이고, 런타임의 미사용 인스턴스 5개를 제거했다. 죽은 사본을
연결하지 **않은** 이유는 분명하다 — 연결하면 살아있는 경로가 둘이 되고, 둘은 언젠가
갈라져 한 질문에 두 답이 생긴다. `advanced.py` 는 계약 참조와 E44 importance/decision
용으로 남기되 그 사실을 파일 상단에 명시했다.

### 측정 방법의 한계도 드러났다

정적 분석(핸들러 소스에서 런타임 속성 이름 찾기)은 두 번 틀렸다. E32 의 `/v1` 핸들러는
다른 함수를 호출하므로 속성 참조가 없고, E39~E43 은 런타임 속성을 지우자 열거에서
아예 사라졌다. **정적 분석은 도달성을 증명하지 못한다.** 그래서 라우트를 실제로 호출해
엔진의 지문(찍힌 id, 그 엔진만 하는 진술)을 확인하는 테스트로 대체했다.

검증: `/v1` 도달성 10건 + 엔진 연결 17건 = **25건**, 실제 HTTP 호출로 확인.

## 11. LLM 계층 L01~L08 — 지시서의 목적만 서로 다르고, 그 넷이 비어 있었다

지시서는 여덟 층 아래에 **동일한 구현 요구 블록**을 그대로 반복한다. 층을 가르는 것은
목적 한 줄뿐인데, 그 목적 중 넷이 구현되어 있지 않았다.

| 층 | 지시서 목적 | 구현 상태 |
|---|---|---|
| L02 | 난이도·비용·지연·**구독 등급**으로 template/fast/standard/reasoning 선택 | task_type 만 봤음 |
| L04 | 필요한 것만 **최소 컨텍스트**로 조립 | 패킷 전체를 덤프했음 |
| L05 | 일반/애호가/연구자/운영자 **4단계** | 목소리가 하나였음 |
| L08 | Daily/Mission/Event/Research·Scenario **4종** | 보고서가 하나였음 |

자격증명이 필요 없는 부분을 모두 만들었고, 외부 공급자 어댑터만 `EXTERNAL_DATA_GATED`
로 남긴다.

### 같은 정직성 규칙을 LLM 계층에도 적용했다

`max_pc_basis` 에서 세운 규칙이 여기서도 그대로 문제가 된다. **생산되지 않은 값은 0이
아니다.**

- 공급자가 토큰 수를 보고하지 않으면 `None` + `NOT_REPORTED_BY_PROVIDER`. `0`은 하지
  않은 측정을 한 것처럼 만든다.
- 가격표가 없으면 비용은 `UNAVAILABLE` + 사유. `0.0`은 공짜라는 뜻이 된다.
- 지연시간은 우리가 직접 잰다. 그래서 `COMPUTED_INTERNAL` 로 표기한다.
- **REASONING 으로 라우팅되어 로컬 템플릿이 응답했다면 `served_tier=TEMPLATE`** 과 그
  사유를 싣는다. 요청한 등급을 실행된 등급처럼 보고하는 것은 남이 계산한 지표를 우리
  것이라 보고하는 것과 같은 결함이다.
- 축소된 컨텍스트는 **축소되었다고 라벨링**한다. `omitted_sections` 가 없으면 소비자는
  "안 보냈다"와 "없다"를 구별할 수 없다.

### 테스트가 내가 만든 결함을 잡았다

OPERATOR 수준에서 금지 주장(`prohibited_claims`)을 산문에 그대로 인용했다. 운영자에게
경계를 알려주려던 것인데, L06 이 그 문장을 발견하고 **답변 전체를 보류**시켰다.

검증기가 옳았고 설계가 틀렸다. 산문은 인용되고 전달된다. 문단 안에 들어앉은 금지
문장은 복사 한 번이면 시스템 자신의 주장으로 읽힌다. 그래서 경계는 **데이터로** 나간다
— `compose()` 가 텍스트 옆에 `prohibited_claims` 목록을 돌려주고, 산문은 그 목록이
있다는 사실만 말한다.

또 하나의 규칙: 등급 상한은 **답을 어떻게 쓰는지**만 바꾸고 **무엇을 담을 수 있는지**는
바꾸지 않는다. TEMPLATE 경로는 어떤 플랜에서도 항상 도달 가능하다. 그래야 지시서의
"안전·공공정보를 결제벽으로 숨기지 않는다"가 지켜진다. 테스트로 고정했다.

검증: L01~L08 계약 **39건**.

## 12. 인수 매트릭스 — 매핑 공백이었지 커버리지 공백이 아니었다

`NOT_YET_MAPPED` 277건은 전부 `test_master_acceptance[<test_id>]` 가 이미 돌리고 있던
행이었다. 파라미터 id 가 매트릭스 `test_id` 와 **같기 때문에** 매핑이 매트릭스와 어긋날

그런데 그대로 "커버됨"이라고만 적으면 과장이 된다. 그 노드 뒤의 디스패치가 행마다

- `ENGINE_DISPATCH[module](case)` — E08~E44 는 모듈별 함수가 케이스별로 분기한다.
- `llm_acceptance` — L01~L08 은 "provider/tool path success" 만 모듈로 분기하고, 나머지

- `_platform_acceptance` — S01~S12 도 "happy path contract" 와 (S03~S12 한정)

요약에까지 싣게 했다.

초록 총합만 보이던 자리에 내분이 함께 보인다.

### 가져온 v0.6 매트릭스가 자기 자신을 PASS 라고 선언하고 있었다

`config/AETHERUS_V2_ACCEPTANCE_MATRIX.csv` 는 커밋 `83197d53` 에서 **이미 307행 전부

가져온 계약 자산은 손대지 않았다. 고친 것은 그것을 우리 증거로 읽던 테스트다.

- 인수 구동부가 `status` 열을 읽지 않는다는 것을 테스트로 고정했다. 초록 CSV 가
  스위트를 초록으로 만들 수 없어야 한다.

이 저장소의 인수 상태는 `artifacts/evidence/acceptance.json` 하나뿐이고, 그 값은 실행된
테스트의 종료 코드에서만 나온다.

## 13. 단계 점수표가 없던 일곱 단계

### P15 의 PARTIAL 은 결함이 아니라 순서다

지시서가 스테이징 증거를 먼저, 운영 결정을 그 다음에 두었다. 자격증명 없이
`staging_ready=True` 가 나오면 준비된 것이 아니라 검사가 고장 난 것이다. 그래서
`staging_not_claimed_without_evidence` 를 **통과해야 하는 검사**로 넣었다 — 스테이징이
근거 없이 주장되면 이 검사가 거짓이 된다.

운영 전환은 `DECISION_PENDING` 이다. 사람이 내리는 결정을 생성기가 대신 내리지 않는다.

### 여기서도 두 가지를 하나의 404 로 뭉치고 있었다

`server_state` 가 404 를 전부 "구식 빌드"로 읽었다. 그런데 404 는 서로 다른 두 질문에
같은 숫자로 답한다 — **"이 배포에 그런 경로가 없다"** 와 **"이 배포에 그런 임무가
없다"**. 앞은 구동 중인 프로세스가 코드보다 오래됐다는 뜻이고, 뒤는 경로가 의도대로
동작한다는 뜻이다.

그 결과 정상 동작하던 `/v1/missions/{id}/state` 의 "mission not found" 가 구식 빌드로
기록됐다. 라이브 OpenAPI 스키마에서 경로 집합을 읽는 방식으로 바꿨고, 스키마를 읽을
수 없는 경우는 `UNKNOWN_BUILD` 로 따로 뒀다 — 경로 집합을 모르는 것과 짧다는 것을
아는 것은 다르다.

이 구분을 `tests/unit/test_phase_evidence_helpers.py` **16건**으로 고정했다.

### 실제로 구식 서버였던 것도 하나 있었다

8100 에서 돌던 uvicorn 프로세스가 라우트 추가 이전(09/02 23:20)에 뜬 것이어서 P13 의

그 둘을 구분해 기록했기 때문에 어느 쪽인지 알 수 있었다.

### 이름이 같은 P5 가 둘이다

V2 단계의 P5(임무 추적, E16~E19)와 궤도 서비스의 "P5 준수 반사실"

거짓말이다.

## 14. 근접 신호가 이벤트가 되지 못한 것은 부품이 없어서가 아니었다

P10 의 유일한 우리 몫 미충족 항목이었다. 어댑터·게이트·상관기·개정 빌더가 전부 있었고
**아무도 호출하지 않았다.** 신호는 `GET /v1/intelligence/signals` 핸들러 **안에서**
만들어져 응답에 합쳐지고 버려졌다. 그래서 살아있는 근접 후보 200건이 있는데 이벤트
저장소에는 픽스처 발사 하나뿐이었고, "무엇이 바뀌었나"는 바뀔 것이 없었다.

승격을 **명시적 POST** 로 만들었다. 이벤트를 만드는 GET 은 이벤트 저장소를 "누가
쳐다봤는가"의 함수로 만든다.

### 재실행이 역사를 만들어내지 않는다

`created` / `revised` / `unchanged` 를 따로 센다. 반복 실행에서 가장 흔한 결과가
`unchanged` 이고, 그것을 성공에 합치면 아무 일도 안 한 실행이 진전처럼 보인다.

### 개정이 기다린 것은 바깥세상이 아니라 질의였다

승격은 각 근접의 **최신** 스냅샷만 실었다. 그런데 스냅샷 테이블은 append-only 라
DB 에 **이벤트 116,119개에 스냅샷 228,426개** 가 이미 쌓여 있었고, 그중 **2,468건은
miss distance 가 1 m 넘게 움직였다** (최대 23 km). 지시서가 요구한 "무엇이 바뀌었나"
기록이 우리 DB 안에 있었고 아무도 읽지 않았다.

`list_conjunction_history` 를 추가했다. `list_conjunctions` 와 컬럼이 같고 스냅샷
선택만 다르다 — 최신 하나가 아니라 기록된 순서대로, 이벤트당 상한을 두고. 상한에
걸린 이벤트는 목록으로 보고한다. 잘린 이력이 잘렸다고 말하지 않으면 전체 기록처럼
읽힌다.

### 그리고 잡음과 변화를 가르는 규칙이 필요해졌다

한 쌍의 스냅샷 네 개가 **9초 안에** 찍혀 있고 miss distance 가 소수점 아홉째 자리에서
갈렸다: 2368.8409795537696 / …530972 / …535041 / …5351845. 같은 계산을 네 번 한
것이지 근접이 움직인 것이 아니다. 그대로 승격하면 아무것도 안 바뀐 변화 네 건이
이벤트 이력에 남고, 진짜 움직인 2,468건이 그 사이에 묻힌다.

`SCREENING_MATERIAL_CHANGE_V1` — 버전과 근거가 붙은 정책이다. 공개 GP 스크리닝
기하는 미터 아래로 분해되지 않으므로 1 m 미만은 산술이 저 혼자 떠든 것이다. 확률
채널은 **상태 변화**면 크기와 무관하게 변화이고, 값은 1% 상대 변화부터 변화다.

### 제외 목록으로 만들었다가 즉시 틀렸다

첫 구현은 "출처 키만 빼고 나머지 전부"였다. `snapshot_id` 와 `snapshot_at` 을 뺐고,
그 다음 **870건의 개정** 을 만들었는데 사유가 `config_hash`·`input_hash`·
`screening_run_id` 였다. 스크리너가 다시 돌았다는 뜻이지 근접이 움직였다는 뜻이 아니다.

제외 목록은 앞으로 누가 추가할 모든 출처 필드를 미리 알아야 한다. **허용 목록**으로
뒤집었다 — 평가 채널로 이름 붙은 것만 변화가 될 수 있다. 이쪽 실패는 "일어났어야 할
개정 하나를 놓침"이고, 그건 "일어나지 말았어야 할 개정 천 건"보다 알아채기 쉽다.

교정 후: 스냅샷 950건 중 **개정 150건, 무변화 720건.** 6:1 이 정책이 거른 양이다.

### HOW SURE 는 패킷이 있어야 답이 된다

`/v1/intelligence/events/{id}/confidence` 는 저장된 패킷을 읽는다. 근접 이벤트에는
패킷이 없어 404 였다. 라우트는 옳았다 — 지어낸 신뢰도는 없는 것보다 나쁘다 — 하지만
관문의 절반이 픽스처에만 답할 수 있었다. 승격이 패킷도 만들게 했다. 서술 문장은 신호와
개정 델타에서만 조립하고, 이전 개정이 없으면 "아직 바뀐 것 없음"이라고 적는다. 첫
관측을 변화라고 쓰지 않는다.

### 등급이 정책의 일부만으로 계산되고 있었다

근접 후보의 신뢰도가 **0.6 / HIGH** 로 나왔다. 유도 가능한 요인이 completeness 와
validation 둘뿐이었고, 점수는 그 둘의 가중평균이다. 즉 정책 가중치 1.0 중 0.25 만
적용된 점수가 전부 적용된 점수와 **같은 0~1 척도, 같은 등급표** 위에 놓인다.
covariance 도 교차검증도 없는 SCREENING_ONLY 후보가 HIGH 로 읽힌다.

점수와 등급은 그대로 뒀다. 채점 정책을 다시 맞추는 것은 수리가 아니라 제품 결정이다.
대신 **적용된 가중치 비율을 평가에 싣는다** (`CONFIDENCE_PARTIAL_BASIS`). 숫자를
조용히 재조정하면 오해를 부르는 숫자를 다른 오해를 부르는 숫자로 바꾸는 것이다.

결과: **P10 gate=PASS.** 이벤트 60건을 조사해 54건에 개정이 둘 이상, 한 이벤트 최대 3건.
P9 의 `conjunction_events_promoted` 도 함께 충족됐다.

### 검사가 자기 자신을 방해하고 있었다

전체 회귀에서만 `test_disagreement_is_preserved_not_overwritten` 이 실패했다. 이 파일의
테스트 15개가 각각 `base + uuid4().int % 900` 으로 카탈로그 id 를 뽑고 **새 것이라고
가정** 한다. DB 는 영속이고 스위트는 수백 번 돌았으므로 900칸 대역은 찬다. 두 번째
수집이 기존 행을 만나 `len(conflicts) == 1` 이 2를 봤다.

오늘 `999999999` 에서 고친 것과 같은 병 — 테스트가 DB 내용을 가정한다. 15곳 모두
부재를 확인하고 쓰도록 바꿨다.

검증: 승격 계약 **18건**, 신뢰도 부분근거 **3건**, 전체 회귀 **1035 passed, 0 failed.**

## 15. 우리 생성기 안에도 손으로 쓴 False 가 있었다

12절에서 가져온 인수 매트릭스가 **자기 자신을 PASS 라고 선언**하고 있던 것을 지적했다.
같은 모양이 우리 코드에도 있었다.

`playwright_e2e_run` 은 세 생성기에서 **리터럴 `False`** 였고, 사유는 "러너 설치와
스크립트 작성만 남았다"였다. 둘 다 쓰일 당시엔 참이었고 지금은 둘 다 거짓이다 —
`tests/e2e` 에 Playwright 스위트 세 개가 있고 통과한다. 그래서 단계 점수표 셋이 이미
닫힌 공백을 보고하고 있었고, 그것도 측정이 아니라 손으로 쓴 값으로 보고했다.

각 생성기가 **자기 표면을 모는 스위트**를 실행하고 종료 코드를 취하게 했다. 매핑은
파일 이름에서 추정하지 않고 단계별로 명시했다 — e2e 파일 이름은 궤도 계보(P3/P4/P5)를
따르는데 이 생성기들이 보고하는 것은 V2 계보이고, 번호로 맞추면 한 단계의 증거가 다른
단계의 관문에 붙는다.

결과: **p3 의 `playwright_e2e_run` 이 측정으로 충족(2 passed), p6 은 PASS 로 전환.**

### p7 은 여전히 미충족이지만 이유가 달랐다

잔해·관측 표면을 모는 스위트가 **없다.** 러너가 없는 것이 아니다. 사유를 그대로
고쳤다. 다른 단계의 스위트를 빌려 오면 그 증거가 이 관문에 붙으므로, 없으면 없다고
적는 편이 맞다.

### 남은 우리 몫 둘

| 단계 | 항목 | 상태 |
|---|---|---|
| p7 | `playwright_e2e_run` | 잔해·관측 E2E 스위트 미작성 |
| p8 | `large_scale_benchmark_run` | 전 카탈로그 스크리닝 약 40분(2,851객체·약 200만 쌍) 실행 미수행 |

p8 의 벤치마크는 실행하지 않았다. 40분 동안 약 200만 쌍을 평가하고 스냅샷을 대량
기록하는 일이며, 14절에서 확인했듯 반복 스크리닝은 실제로 무변화 스냅샷을 쌓는다.
규모와 저장 결정은 PD 의 몫이라 판단했고, 측정된 비용을 그대로 적어 둔다.

최종: 단계 16개 중 **PASS 6, PARTIAL 10.** PARTIAL 10개 중 8개는 자격증명·파트너·사람의
결정만 남았고, 우리 몫은 위 둘뿐이다.
