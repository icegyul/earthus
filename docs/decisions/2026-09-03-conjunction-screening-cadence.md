# 결정 — 자체 광역 충돌 스크리닝을 예약 실행하지 않는다

2026-09-03 · 결정자 PD · 근거는 전부 실측

## 결정

**자체 all-vs-all 충돌 스크리닝을 정기 실행으로 켜지 않는다.** 앞을 내다보는 근접
예상은 CelesTrak SOCRATES 수집으로 충당하고, 자체 스크리닝은 온디맨드(데모·검증·
연구)로만 돌린다.

유료 고객이 생겨 특정 위성에 대한 정확한 답이 요구될 때, all-vs-all 이 아니라
**관심목록 × 전 카탈로그** 모드를 만들어 그때 켠다.

## 왜 — 세 가지 실측

### 1. 주기를 늘려도 비용이 줄지 않는다

비용이 `쌍 수 × 덮는 시간축 길이`다. 실행 횟수가 아니다.

```
매일 × 24시간 창   1주 커버 = 376.5 CPU-시간
주 1회 × 7일 창    1주 커버 = 376.5 CPU-시간
차이 = 고정비 56초 (전체의 0.003%)
```

실행당 고정비(카탈로그 적재 0.4s + prepare 0.1s + 껍질 필터 8.8s ≒ 9.3초)는 창 길이와
무관하지만 전체의 0.003%라 주기로 아낄 것이 없다. **주기를 줄여 싸지는 경우는 덮는
시간을 포기할 때뿐이다.** 15분 창을 하루 한 번 돌리면 하루 중 15분만 본다.

### 2. 연속 커버리지가 실시간을 못 따라간다

전 카탈로그 1회 실측: 객체 19,672 / 쌍 193,483,956 / 이벤트 20,104 / 창 0.25시간 /
**2,026초**. 시간축 1시간을 덮는 데 2.24 CPU-시간이므로 하루를 빈틈없이 덮으려면
**54 CPU-시간/일** — 실시간의 2.25배다. 어떤 주기로 쪼개도 따라잡을 수 없다.

### 3. 7일 앞 예상은 이미 무료로 온다

| 출처 | 이벤트 | TCA 범위 | 비용 |
|---|---|---|---|
| SOCRATES(CelesTrak) | 105,567 | 7일 앞까지 | HTTP 페치 |
| 자체 all-vs-all | 29,156 | 20시간 앞까지 | 376 CPU-시간/주 |

겹침은 0.4%라 중복은 아니지만, 거리 분포가 역할을 가른다.

| 출처 | <1km | 1–5km | 5–15km | >15km |
|---|---|---|---|---|
| 자체 | 665 | 2,530 | 8,753 | **17,124** |
| SOCRATES | 4,909 | 100,618 | 26 | 0 |

**우리 출력의 89%가 5 km 이상**이고 그 대역은 외부 피드가 위험하지 않다고 보아 아예
내지 않는다. 정작 위험 대역(<1km)은 외부가 7배 촘촘하다. 즉 자체 광역 스크리닝은
376 CPU-시간을 써서 남이 이미 더 잘 주는 것을 더 못하게 다시 만들고 있었다.

## 유지비

| | 컴퓨트 | 데이터 | 연 비용 |
|---|---|---|---|
| **채택: SOCRATES 수집만** | ~0 (HTTP) | 연 수 GB | **1만 원 미만** |
| (참고) 자체 광역 추가 시 | 376 CPU-시간/주 | 연 1.7~12 GB | 2~3만 원 + 서버 |

## 이 결정이 바꾸지 않는 것

- **`/api/v1/conjunctions/screen-runs` 는 그대로 둔다.** 온디맨드 실행·테스트·증거
  생성이 이 경로를 쓴다. 끄는 것은 예약 실행이지 기능이 아니다.
- **임계값 25 km 도 그대로 둔다.** 5 km 로 낮추면 89% 가 줄지만 그것은 탐지 범위를
  바꾸는 제품 결정이고, 유지비가 이미 작아 비용을 근거로 좁힐 이유가 없다.
- **스냅샷 물질적 변화 정책은 유지한다.** 온디맨드 실행에도 그대로 적용되어 재기록을
  86% 줄인다.

## 되돌리는 조건

다음 중 하나가 참이 되면 이 결정을 다시 본다.

1. 유료 고객이 특정 위성에 대한 근접 답을 요구한다 → 관심목록 × 전 카탈로그 모드를
   만든다. 관심 100개면 1,960,650 쌍으로 all-vs-all 의 1% 라 연속 커버리지가 하루
   33분이면 되고, 비용이 고객 수에 선형이라 과금 단위와 맞는다.
2. SOCRATES 가 끊기거나 정책이 바뀐다 → 자체 스크리닝이 유일한 출처가 되므로 켠다.
3. 5 km 미만 대역에서 외부 피드가 놓치는 것이 관측된다 → 그 근거를 들고 다시 본다.

## 선행 조건 하나

자체 스크리닝을 언젠가 켤 때를 위해, **스크리닝을 API 이벤트 루프 밖으로 빼는 작업**이
먼저 끝나야 한다. 지금은 도는 동안 `/health` 응답이 6.8 ms → 최대 9.17초로 늘어난다
(400객체 실행 중 실측). 별도 작업으로 진행 중.

## 부기 — 결정 직후 관측된 것 (2026-09-03)

이 결정을 기록하는 중에 E2E 스위트가 위 진단을 실사례로 보여 줬다.

`tests/e2e/test_p5_remove_panel.py` 가 첫 `page.goto("/ui/")` 에서 30초 타임아웃으로
실패했다. 테스트가 뭘 하기도 전이고, 같은 순간 curl 로는 `/ui/` 가 0.32초에 200을
돌려주다가 곧 35초 무응답으로 바뀌었다.

서버 프로세스를 보니 **CPU 500초를 태우며 돌고 있었고**, 마지막 로그가
`load_screenable_solutions(2000)` 이었다. 즉 브라우저 테스트 하나가 P5 체인을 통해
**기본 설정(24시간 창 × 2,000객체) 스크리닝**을 유발했고, 그것이 동기로 돌며 API 를
막았다. 24시간 창은 아무도 재 본 적이 없는 조합이고, 6시간 창이 2,000객체에 2,844초
였으니 수천 초 단위다.

세 가지가 여기서 드러난다.

1. **이벤트 루프 차단은 이론이 아니라 지금 테스트를 깨고 있다.** 진행 중인 분리 작업이
   가설이 아니라 관측된 고장을 고치는 일이다.
2. **긴 계산을 유발하는 경로에 상한이 없다.** 루프 밖으로 빼도 브라우저 클릭 한 번이
   수천 초짜리 계산을 시작시키는 문제는 남는다. 그 경로에 범위 상한이 필요하다.
3. **기본 창 24시간이 아무도 안 재 본 채 기본값으로 앉아 있다.** 이 결정으로 예약
   실행은 안 하지만, 온디맨드 경로가 그 기본값을 그대로 쓴다.

이 관측은 이 결정을 바꾸지 않는다 — 오히려 지지한다. 자체 광역 스크리닝은 켤 준비가
안 되어 있다.

## 후속 — 폭주를 계약으로 막았다 (2026-09-03)

부기에서 관측한 폭주에 상한을 넣었다. **끄는 것으로 끝내지 않고, 다시 그렇게 될 수
없게 했다.**

### 무엇이 폭주를 허용하고 있었는지

| 설정 | 이전 | 이후 | 근거 |
|---|---|---|---|
| `screening_window_hours` | 24.0 | **2.0** | 24시간 조합은 실행된 적이 없다. 2시간은 실측(2,000객체 429~490초) |
| `benefit_horizon_hours` | 24.0 | **2.0** | 브라우저 클릭이 건드린 값이 이것이다 |
| `MAX_WINDOW_HOURS` | 168.0 | **24.0** | 6시간을 넘겨 측정된 실행이 없는데 7일을 계약으로 허용하고 있었다 |
| `MAX_HORIZON_HOURS` | 168.0 | **24.0** | 같은 이유 |
| 작업 예산 | 없음 | **12,000 객체시간** | 실측 최대(1,998×6h = 11,988, 47분) 바로 위 |

### 예산을 12,000 에 둔 이유

처음에 5,000 으로 잡았더니 **실제로 47분에 완주한 6시간 창 실행을 거부했다.** 사람이
이미 성공적으로 해낸 일을 막는 가드는 꺼진다. 그래서 측정된 최대 바로 위에 두고,
빠른 기본 경로는 예산이 아니라 기본값이 맡게 했다.

```
2,000 x 24h = 48,000 객체시간  -> 거부 (최악 5.5시간)   ← 폭주했던 조합
19,700 x 24h = 472,800         -> 거부 (최악 54시간)
2,000 x  2h =  4,000           -> 통과 (실측 429초)     ← 새 기본값
19,657 x 0.25h = 4,914         -> 통과 (실측 2,026초)   ← 전 카탈로그 벤치마크
1,998 x  6h = 11,988           -> 통과 (실측 2,844초)   ← 실측 최대
```

### 거부이지 잘라내기가 아니다

창을 몰래 줄이면 요청한 것과 다른 질문에 답하고 그 결과가 요청한 것처럼 보인다.
모집단 상한(`max_objects`)은 잘라내지만 `population_truncated` 라벨이 함께 나간다.
창에는 그런 라벨이 없으므로 거부하고 무엇을 줄이면 되는지 말한다.

실측 응답:

```
HTTP 422 in 0.62s
SCREEN_BUDGET_EXCEEDED
"screening work 472,800 object-hours (19,700 objects x 24 h) exceeds the
 12,000 object-hour budget; ... Reduce the window to 0.61 h or fewer at this
 population, or lower max_objects."
```

54시간짜리 요청이 0.62초에 끝나고 UI 는 계속 응답한다. 처음엔 500 이 나갔는데, 너무
큰 요청은 서버 잘못이 아니라 호출자 문제이므로 도메인 오류 분류에 편입해 422 로
바꿨다. 숫자 없는 "too big" 은 받은 사람에게 막다른 길이다.

### 아직 남은 것

**브라우저 클릭 하나가 여전히 수 분을 태운다.** 예산은 모집단 적재를 막았을 뿐
반사실 전체 작업은 아니다. `POST /api/v1/scenarios/{id}/run` 이 `catalog_scope` 를
넘기지 않아 매번 기본 모집단 2,000 을 다시 계산한다 — 그런데 이 저장소 자신의 규칙이
REMOVE 는 베이스라인 모집단으로 스코핑해도 건전하다고 말한다. 별도 작업으로 띄웠다.

이벤트 루프 분리 작업과 **둘 다 필요하다.** 루프 밖으로 빼도 클릭 하나 뒤에 수 분짜리
계산이 남아 있는 것은 그대로다.

검증: 예산 계약 **18건**, 전체 회귀 **1,067 passed** (E2E 1건은 위 잔여 문제).
