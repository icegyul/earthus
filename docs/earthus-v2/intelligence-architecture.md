## 1. 오늘의 구조 — 두 개의 인텔리전스가 서로 모른다

지침서 §3.4 는 우측 패널을 "전역 메뉴에서 문맥 결과로" 바꾸라고 한다. 감사 결과 문제는 그보다 하나 더 있다. **질문하는 곳과 결과가 나오는 곳이 아예 다른 화면이다.**

| | 우측 `#intel` 패널 | 질문 서랍 `#ask-drawer` |
|---|---|---|
| 위치 | 우하단 | **좌상단 `#panel` 안** |
| 생성 | `ui-shell.js:443-463` 이 JS로 만든다 (index.html 에 마크업 없음) | 별도 |
| 탭 | 6개 고정 (사건·내 지역·선택 자료·자료의 근거·예보·시뮬레이션) | 없음 |
| 문맥 | 6개 중 5개가 **전역**이다 | 카메라 좌표 + 켜진 레이어 id |
| 서로 | **연결 없음.** `askEarth.close()` 는 아무 데서도 안 부른다 | 우측 패널을 건드리지 않는다 |

`/api/ask` 페이로드에 **현상이 없고 사건도 없다.** 카메라 위경도, 화면 중앙 표본, 초점 국가, 켜진 레이어 id 뿐이다. 그래서 "지금 이 태풍" 을 물어도 모델이 받는 것은 좌표와 레이어 목록이다.

답변 스키마는 `answer / insufficient / used[] / actions / model / tokens` 다. **신뢰도도, 불확실성도, 주장별 인용도 없다.** `used[]` 는 모델이 스스로 주장한 문자열이고, 그것을 다시 충돌하는 bare-id `layerIndex` 로 해석한다.

## 2. 이미 있는 정답 하나 — 이것을 확장한다

우측 패널에 **진짜 문맥 결과가 이미 하나 있다.** `eventNextHtml`(`ui-shell.js:558-568`)은 `hooks.feedNext` 를 받아 KMA·JMA·NHC·ECMWF 기관별 +24h/+48h 표를 그린다.

새로 만들지 않는다. **이 패턴을 넓힌다.**

- `#intel-content` 의 소유권을 가져오지 않는다. `ext-scene.js:304` 가 19개 LAB·취미 모듈을 위해 같은 노드를 이미 쓴다. 뺏으면 그 19개가 죽는다.
- `renderIntel` 은 `innerHTML` 을 통째로 갈아끼우고 스크롤을 손으로 복원한다. 부분 갱신으로 바꾸지 말고 **그리는 내용만** 바꾼다.
- `feedSelected`(`main.js:4287`, 지금 `{title, kind}`)를 넓혀 현상 id 와 사건 id 를 싣는다.

## 3. 먼저 있어야 하는 것 두 가지

### 3.1 선택 상태를 읽는 함수 (`getSelection`)

`selectedMenu` 는 `ui-shell.js:259` 의 클로저 사적 변수다. `setSelection`·`clearSelection` 은 있는데 **읽는 함수가 없다.** 문맥 패널은 "지금 무엇이 선택되어 있나" 를 알 수 없으면 문맥이 될 수 없다.

→ `ui-shell` 반환 API 에 `getSelection()` 을 추가한다. 이것이 PHASE 3 의 첫 줄이다.

### 3.2 안정된 사건 주소 (Event id) — 패널보다 **먼저**

지금 사건 방은 **배열 인덱스**로 주소를 잡는다(`intel-feed.js:428` `data-idx`). 그 배열은 정착할 때마다 재정렬된다. 게다가 FOR ME 카드는 폭풍 이름을 대문자로 바꿔 역매핑한다(`main.js:3293-3299`).

**주소가 흔들리는 위에 문맥 패널을 지으면 패널이 흔들린다.** 그래서 지침서 STEP N 의 Event 부분을 STEP E 앞으로 당긴다(§6, phase-0-audit).

사건 객체는 지금 종류별로 필드가 다른 인라인 리터럴 두 개다(`intel-feed.js:304`, `:346`). 정본 형태는 이미 저장소에 있다 — `v11/event/event-fusion.js` 의 `clusterEarthEvents`. 다만 필드 이름이 피드 쪽과 의미가 충돌하므로 그대로 쓰지 말고 대조한 뒤 채택한다.

## 4. 요청 형태

지침서 §6.1 을 레지스트리 위에 얹는다.

```js
getIntelligence({
  phenomenonId,      // 'hazards.typhoon' — LAYER_PHENOMENON 에서 온다
  layerKey,          // 'hazards/tyoff'  — 복합키. bare id 를 쓰지 않는다
  eventId,           // 안정된 사건 id (3.2 가 선행)
  focus,             // 카메라/선택 지점
  at,                // 시각
  question,          // 레지스트리의 질문 id
})
```

`phenomenonId` 가 필수인 이유는 단순하다. **답의 형태가 현상마다 다르기 때문이다.** 낙뢰에 태풍의 앙상블 일치도를 물을 수 없다.

## 5. 답변 계층 — 없는 것은 만들지 않는다

지침서 §6.2 의 계층(관측 → 해석 → 영향 → 예보 → 불확실성 → 근거)을 쓰되, **레지스트리의 능력 플래그가 어떤 계층을 낼 수 있는지 결정한다.**

| 계층 | 낼 수 있는 조건 |
|---|---|
| 관측 | `capabilities.current` |
| 사료 | `capabilities.history` |
| 해석 | `capabilities.intelligence` |
| 예보 | `capabilities.forecast` |
| 불확실성 | 예보/분석에 구간·앙상블 폭이 있을 때만 |
| 근거 | `capabilities.evidence` |

`intelligence:false` 인 현상은 **해석 계층을 비운다.** 지어내지 않는다. 오늘 그런 현상이 22개다.

구체적으로 낙뢰: `intelligence:false` 다. 자기 질문은 "주변에 낙뢰가 있었나" 인데 `live-layers.js` 의 `metaLightning` 은 **전국 합계**(총 낙뢰 수·대지방전 수·최대 kA)만 낸다. 근접 판정은 하지 않는다.

**그런데 이것이 가장 값싼 수리다.** 낙뢰 기록은 이미 위경도를 들고 있다. `event-room.js` 에 낙뢰 행이 없고 `for-me-signal.js` 에 낙뢰 카드가 없을 뿐이다. 지침서 §6.4 가 요구하는 근접 임계 판정은 **새 자료 없이** 가능하다.

## 6. LLM 의 자리 (지침서 §32)

LLM 은 승인된 사실을 **서술**한다. 계산하지 않는다.

지금은 그 경계가 없다. 강제할 지점:

1. `used[]` 를 모델의 자기 신고에서 **호출자가 실제로 넘긴 사실 목록**으로 바꾼다. 모델이 인용을 발명할 수 없게 한다.
2. `ask` 페이로드에 `ageMin`/`slaMin` 을 실어 서버의 신선도 규칙(`handler.py:55`)을 되살린다 — **지금 그 코드는 죽어 있다.** 클라이언트가 값을 안 보내기 때문이다.
3. 답변에 신뢰도 필드를 넣되, **모델이 만들지 않는다.** 자료의 `evidenceProfile` 과 신선도에서 파생한다.

## 7. 중복 어휘 정리 (지침서 §29)

같은 것을 부르는 이름이 사건 6개, 내 위치 6개다. 공개 어휘를 하나로 고정한다.

| 개념 | 공개 이름 | 내부 구분 |
|---|---|---|
| 사건 | **사건** | 피드 서비스 · Event 엔티티 · 사건 방 |
| 내 장소 | **내 지역** | 등록 장소 / 카메라 초점 / 선택 사건 — 셋을 내부에서 분리 |

주의: 우측 탭 라벨 6개와 하단 6개는 **i18n 키가 아예 없다**(`ui-shell.js:449-458`, `:481-488` 의 인라인 삼항). 사전만 고쳐서는 이름이 안 바뀐다.

## 8. 순서

1. `getSelection()` 추가 (5줄)
2. Event id 도입 — 배열 인덱스 주소 제거
3. `feedSelected` 를 현상·사건까지 싣도록 확장
4. `eventNextHtml` 패턴으로 문맥 블록 확장 (소유권 이동 없음)
5. `/api/ask` 에 현상 문맥 추가, `used[]` 를 호출자 사실로 교체
6. 낙뢰 근접 판정 — `intelligence:false` 를 참으로 바꾸는 첫 사례
