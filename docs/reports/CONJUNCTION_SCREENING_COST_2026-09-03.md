# 충돌 근접 스크리닝 — 운영 비용 보고

2026-09-03 · 전부 실측값. 추정한 항목은 그렇게 표시했다.

---

## 한 줄

**자체 광역 스크리닝은 켜지 않기로 했다. 7일 앞 예상은 CelesTrak SOCRATES 가 이미 무료로 주고, 우리가 376 CPU-시간/주를 써서 그것을 더 못하게 다시 만들고 있었다.** 유지비는 연 1만 원 미만으로 내려간다.

결정 기록: `docs/decisions/2026-09-03-conjunction-screening-cadence.md`

---

## 1. 무슨 기능인가

앞으로 정해진 시간 안에 궤도 물체 **둘이 25 km 안으로 스쳐 지나가는 순간**을 전부 찾아낸다. 위성 운영자가 "내 위성이 언제 무엇과 몇 미터까지 붙는가"를 아는 기능이고, 회피 판단의 근거가 된다.

실제 출력:

```
LEMUR-2-LAILA  x  ETIHAD-SAT      09-05 13:07    500 m
STARLINK-31638 x  2024-153F       09-03 01:19    500 m
STARLINK-4383  x  STARLINK-4658   09-06 17:25    500 m
```

동작은 단순하다. 카탈로그의 궤도 정보를 앞으로 전파하고, 30초 간격으로 쌍의 거리를 재서, 임계값 안에 들어오는 쌍을 기록한다.

---

## 2. 얼마나 쓰는가 — 컴퓨트

전 카탈로그 실행을 실제로 완주했다.

| 항목 | 실측 |
|---|---|
| 객체 | 19,672 |
| 쌍 | 193,483,956 |
| coarse 통과 | 235,867 |
| 찾은 이벤트 | 20,104 |
| 예보 창 | 0.25시간 |
| **소요** | **2,026초 = 33.8분** |

주기별 연간 컴퓨트:

| 주기 | 연간 CPU-시간 |
|---|---|
| 매일 | 205 |
| 주 1회 | 29 |

**이 표를 절감으로 읽지 말 것.** 같은 예보 창을 유지한 채 주기만 늘리면 덮는 시간축이
같이 줄어든다. 6절 참조.

**전용 서버가 필요 없는 규모다.** 하루 0.56 CPU-시간이면 이미 돌리는 API 서버가 흡수한다. 단, 지금은 스크리닝이 API 이벤트 루프를 막아서 도는 동안 응답이 6.8 ms → 최대 9.17초로 늘어난다. 이 문제는 별도 작업으로 진행 중이고, 해결되면 같은 서버에서 돌려도 된다.

### 비용을 정하는 손잡이는 예보 창이다

객체 수가 아니라 **몇 시간 앞을 보느냐**가 지배 변수다. 대략 `창^1.5`로 늘어난다.

| 창 | 객체 | 소요 | 편차(반복 측정) |
|---|---|---|---|
| 0.25시간 | 5,000 | 68~72초 | 1.1배 |
| 2시간 | 1,998 | 429~490초 | 1.1배 |
| 6시간 | 1,998 | 2,181~2,844초 | 1.3배 |

측정 자체는 매우 안정적이다(1.1~1.3배). 24시간 창은 아직 아무도 돌린 적이 없고, 지금 필요도 없다.

## 3. 데이터가 얼마나 늘어나는가

단위 실측: 스냅샷 1.70 KB, 이벤트 0.61 KB (인덱스 포함).

| | 실행당 | 매일 | 주 1회 |
|---|---|---|---|
| 첫 실행 | 45.4 MB | — | — |
| **절감 적용** (실측 14%) | 4.7 MB | **1.7 GB/년** | 0.2 GB/년 |
| 절감 미적용 | 33.4 MB | 11.9 GB/년 | 1.7 GB/년 |

현재 DB는 570 MB다 (snapshot 490 MB / 299,609행, event 80 MB / 134,709행).

**절감은 이미 적용했다.** 매 실행마다 후보 전부를 다시 쓰던 것을, 평가가 실제로 움직였을 때만 쓰도록 바꿨다. 같은 스크리닝을 연속 두 번 돌린 실측:

```
run 1:  30.5초  후보 1,463  기록 1,261  재사용   202
run 2:  26.7초  후보 1,461  기록   200  재사용 1,261   ← 86.4% 절감
```

이벤트의 `last_seen_at`은 계속 갱신되므로 "봤다"는 사실은 잃지 않는다. 잃는 것은 중복뿐이다.

**14%는 하한이다.** 연속 재실행에서 잰 값이라, 하루 간격으로 돌리면 궤도 정보가 갱신되어 더 많이 쓴다. 그 값은 아직 안 재 봤다. 그래서 위 표에 1.7~11.9 GB/년으로 양끝을 다 적었다.

## 4. 유지비는 얼마인가

**현재 실제 지출은 0원이다.** 배포된 서버가 없고 개발 장비에서 돈다.

배포 시 추가 비용(가정: 관리형 Postgres 스토리지 $0.115/GB/월):

| 항목 | 매일 실행 | 주 1회 |
|---|---|---|
| 스토리지 (1.7~11.9 GB/년) | 연 $2 ~ $16 | 연 $0.3 ~ $2 |
| 컴퓨트 | 기존 서버 흡수 시 $0 | $0 |
| **합계** | **연 2~3만 원** | **연 수천 원** |

컴퓨트를 별도 인스턴스로 빼면 8 vCPU / 32 GB 형상이 월 $30~60이지만, **하루 34분 쓰자고 24시간 인스턴스를 살 이유가 없다.** 이벤트 루프 문제만 해결하면 기존 서버로 충분하다.

## 5. 남은 결정 하나 — 임계값

지금 25 km 안의 모든 근접을 기록한다. 그런데 우리 출력의 분포가 이렇다.

| 출처 | <1km | 1–5km | 5–15km | >15km |
|---|---|---|---|---|
| 자체 스크리닝 | 665 | 2,530 | 8,753 | **17,124** |
| SOCRATES(외부) | 4,909 | 100,618 | 26 | 0 |

**우리가 만드는 것의 89%가 5 km 이상**이고, 외부 피드는 그 대역을 위험하지 않다고 보아 아예 내지 않는다. 임계값을 낮추면 그만큼 줄어든다.

| 안 | 절감 | 대가 |
|---|---|---|
| 5 km | 89% | 5~25 km 접근을 못 봄 |
| 10 km | 약 59% | 10 km 이상을 못 봄 |
| 유지(25 km) | — | 현 상태 |

**이건 비용 결정이 아니라 탐지 범위 결정이다.** covariance가 없어 Pc를 못 구하는 상태에서 거리가 유일한 판별자이므로, 넓게 훑는 데는 이유가 있다. 그리고 위 표대로 유지비가 어차피 작아서, 비용을 근거로 좁힐 필요가 없다.

---

## 6. 주기를 늘려도 싸지지 않는다

가장 늦게 알아낸 것이고 결론을 바꾼 것이다. 비용이 `쌍 수 × 덮는 시간축 길이`라
실행 횟수가 아니다.

```
매일 × 24시간 창   1주 커버 = 376.5 CPU-시간
주 1회 × 7일 창    1주 커버 = 376.5 CPU-시간
차이 = 고정비 56초 (전체의 0.003%)
```

예보 창 15분은 "지금부터 15분 안"만 본다. 하루 1회 돌리면 하루 24시간 중 15분만
들여다보는 것이다. 시간축을 빈틈없이 덮으려면 **실행 주기 ≤ 예보 창**이어야 하고,
그러면 전 카탈로그는 **54 CPU-시간/일** — 실시간의 2.25배라 어떤 주기로 쪼개도
따라잡을 수 없다.

**앞선 5절까지의 "짧은 창으로 싸게 돌린다"는 성립하지 않는다.** 짧은 창은 싼 게
아니라 덜 보는 것이다.

## 7. 결론과 권고

1. **자체 광역 스크리닝은 예약 실행하지 않는다.** 7일 앞 예상은 SOCRATES 가 이미
   준다(105,567건). 우리 출력의 89%는 외부가 위험하지 않다고 걸러낸 5km 이상 대역이고,
   위험 대역은 외부가 7배 촘촘하다.
2. **온디맨드 경로는 남긴다.** 데모·검증·증거 생성이 쓴다. 끄는 것은 주기이지 기능이
   아니다.
3. **임계값 25 km 는 유지한다.** 유지비가 이미 작아 탐지 범위를 좁힐 이유가 없다.
4. **이벤트 루프 분리를 끝낸다.** 언젠가 켤 때의 선행 조건이다.
5. **유료 고객이 생기면 관심목록 × 전 카탈로그를 만든다.** 관심 100개 = 1,960,650 쌍
   으로 all-vs-all 의 1%, 연속 커버리지가 하루 33분. 비용이 고객 수에 선형이라 과금
   단위와 맞는다.
