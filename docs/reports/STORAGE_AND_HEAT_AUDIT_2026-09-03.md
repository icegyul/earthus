# 저장 비용·발열 전수 검수

2026-09-03 · 전부 실측

---

## 결론 두 줄

**저장:** `risk_edge` 하나가 DB 7.2 GB 중 **6.5 GB(90.3%)**다. 내가 앞서 줄인
근접 스냅샷은 7.3%였다. 엉뚱한 곳을 최적화하고 있었다.

**발열:** 상시 도는 것이 **하나도 없다.** 스케줄러도 폴링 루프도 상주 워커도 없다.
열은 전부 요청이 있을 때만 나고, 유일한 병렬 구간(스크리닝)은 방금 28코어 중 29% →
11%로 낮췄다.

---

## 1. 저장 비용 — 많이 드는 순

관리형 Postgres 스토리지 $0.115/GB/월 가정.

| # | 테이블 | 크기 | 비중 | 연 비용 | 무엇인가 |
|---|---|---|---|---|---|
| 1 | **risk_edge** | **6,500 MB** | **90.3%** | $8.76 | P5 베이스라인 위험그래프 간선 |
| 2 | conjunction_snapshot | 524 MB | 7.3% | $0.71 | 근접 평가 스냅샷 |
| 3 | conjunction_event | 86 MB | 1.2% | $0.12 | 근접 이벤트 |
| 4 | orbit_solution | 26 MB | 0.4% | $0.04 | 궤도해 |
| 5 | object_metadata_revision | 17 MB | 0.2% | $0.02 | 객체 메타데이터 계보 |
| 6 | 기타 13개 | 47 MB | 0.7% | $0.06 | |
| | **합계** | **7,200 MB** | 100% | **$9.70** | |

디스크는 67 MB로 무시할 수준이다 (증거 24M, 원본 보관 23M, prototype 데이터 19M).

### 1위가 압도적인 이유

`risk_edge` 는 append-only 다. 베이스라인을 지을 때마다 간선 집합 전체를 다시 쓴다.

```
베이스라인 스냅샷      1,397개   (3일간)
risk_edge 행       3,996,540
베이스라인당 평균      3,000 간선  (최대 24,487)
베이스라인당 용량        4.9 MB
```

3일에 1,397개 = **하루 466개**. 사용자가 0명인데도 이렇다. 테스트·E2E·증거 생성이
매번 새 베이스라인을 짓고, 기존 것을 재사용하지 않는다.

**관측된 속도로는 하루 2.2 GB, 연 810 GB, 연 $1,118.**

지금 7.2 GB 는 별것 아니지만 증가 속도가 문제다. 그리고 이 속도는 개발 활동이 만든
것이라 실사용과 무관하다.

### 왜 이게 쌓였나 — 싼 것이 비싸다

| | 실행 비용 | 보관 비용 |
|---|---|---|
| 베이스라인 1회 | **1.1초** | **4.9 MB 영구** |
| 스크리닝 1회 (새 기본값) | 53초 | 643 스냅샷 ≈ 1 MB |

베이스라인은 **돌리기 싸고 보관은 비싸다.** 아무도 막지 않으니 3일에 1,397개가 쌓였다.
스크리닝은 반대라 눈에 띄어서 내가 먼저 손댔는데, 실제 비용은 저쪽에 있었다.

## 2. 발열 검수

### 상시 도는 것: 없음

`while True`, 스케줄러, 주기 폴링, 상주 워커 — 전수 검색 결과 **하나도 없다.**
`asyncio.sleep` 두 건은 공급자 재시도 백오프이고 주입 가능한 인자다.

즉 **아무것도 요청하지 않으면 CPU 는 0 이다.** 검수 시점 전체 부하 5%, 그중 우리
프로세스 기여는 없었다.

### 열을 내는 것: 요청 시 계산 셋

| | 이전 | 지금 | 비고 |
|---|---|---|---|
| **스크리닝 레벨1 스캔** | 8 스레드 = 28코어의 29% | **3 스레드 = 11%** | 유일한 병렬 구간 |
| 스크리닝 1회 (기본값) | 완주 못 함 (최악 5.5시간) | **53초** | 아래 참조 |
| 베이스라인 빌드 | 1.1초 | 1.1초 | 단일 스레드, 열 없음 |
| P5 반사실 | 수 분 | 수 분 | **남은 문제** |

### 이번에 줄인 것

| | 객체 | 창 | 스레드 | 객체시간 | 쌍 | 결과 |
|---|---|---|---|---|---|---|
| 이전 기본값 | 2,000 | 24h | 8 | 48,000 | 1,999,000 | 완주 못 함 |
| 새 기본값 | **500** | **2h** | **3** | **1,000** | **124,750** | **53초 실측** |

총 작업량 **48배 감소**, 순간 점유 **29% → 11%**. 쌍이 제곱이라 객체를 줄인 효과가
가장 컸다.

측정 중 전체 CPU 는 계속 **0~2%** 였다.

## 3. 그래서 무엇을 해야 하나 — 비용 순

### 1순위 — 베이스라인 재사용 (연 $1,118 → 거의 0)

지금은 매 호출이 새 베이스라인을 짓는다. 같은 입력(같은 카탈로그 상태, 같은 지평)에
대해 이미 지어진 베이스라인이 있으면 재사용하면 된다. `input_hash` 가 이미 계산되고
있으므로 그것으로 조회하면 된다.

이건 append-only 규칙을 어기지 않는다 — 새 행을 안 쓰는 것이지 기존 행을 고치는 게
아니다.

### 2순위 — 오래된 베이스라인 만료

과학 기록은 지우지 않는 것이 이 저장소의 규칙이지만, **개발 중 만들어진 1,397개**는
과학 기록이 아니라 테스트 잔해다. 무엇이 잔해인지 구분할 표시가 지금 없다.
(예: `created_by` 에 테스트/데모 표시를 남기고 그것만 만료)

이건 **파괴적 작업**이므로 PD 승인 없이는 하지 않는다.

### 3순위 — P5 반사실 스코핑

이미 별도 작업으로 띄웠다. 발열 쪽 남은 유일한 항목이고, 저장에도 영향을 준다
(반사실 1회 = 베이스라인 1회 = 4.9 MB).

### 하지 않아도 되는 것

- **근접 스냅샷 추가 최적화** — 이미 86% 줄였고 전체의 7.3%다. 더 짜낼 것이 없다.
- **디스크 파일 정리** — 67 MB다. 신경 쓸 규모가 아니다.
- **워커 추가 감소** — 3 스레드면 11%다. 더 줄이면 같은 일이 더 오래 걸릴 뿐이다.
